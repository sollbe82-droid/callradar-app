# 콜레이더(CallRadar) — 사업 정관 목적조항 · 개발/특허 헌장 · 지원사업 로드맵

> 목적: 회사가 나아갈 방향과 "기능을 개발·개혁·혁신할 때마다 지켜야 할 원칙"을 문서로 고정한다.
> 특히 (1) 자사 특허화 가능성 검토와 (2) 타사 특허 침해 여부(FTO) 검토를 **모든 기능 개발의 필수 절차**로 규정한다.
> ⚠️ 본 문서는 실무 초안이다. 정식 정관·특허 청구항·계약은 **법무사·변리사 검토**를 반드시 거친다. (작성 보조: Claude, 법률자문 아님)

## 1. 회사 정체성 (Mission)

콜레이더는 **택시 기사의 운행 데이터를 무입력으로 자동 수집·정규화하고, 이를 기반으로 수요 예측·세무/정산 자동화·신용·산업서비스 중개로 확장하는 모빌리티 데이터 플랫폼(B2B SaaS + 핀테크)**이다.
- 한 줄 정의: "택시 기사의 매출·수요·정산을 자동화하는, 데이터가 쌓일수록 강해지는 앱."
- 정체성 주의: 위치 "탐지/레이더"나 안전·국방 LBS가 **아니다.** "레이더"는 호출을 탐지한다는 브랜드 은유일 뿐. 지원사업·투자 피칭은 **모빌리티/데이터/핀테크** 프레임으로 통일한다.
- 해자(방어막): 특허보다 **누적 데이터**(이종 플랫폼 무입력 수집 + 다수 기사 비식별 제보)가 핵심 경쟁우위다. 특허는 그 시간을 벌어주는 울타리다.

## 2. 정관 「사업의 목적」 조항 — 초안

회사는 다음 각 호의 사업을 영위한다.

1. 모빌리티·운수 분야 응용 소프트웨어(모바일 앱) 개발·공급 및 유지보수업
2. 택시·운수 종사자 대상 운행데이터 자동수집·정규화 및 매출·정산 관리 서비스업
3. 위치·운행 데이터의 비식별 집계·분석 및 수요 예측 정보 제공업
4. 데이터 기반 세무·회계·정산 자동화 및 관련 소프트웨어 서비스업
5. 운행·매출 데이터 기반 신용평가 보조·소득증빙 생성 등 핀테크 연계 서비스업
6. 택시 산업 서비스(연료 충전·정비·보험·금융 등) 중개·매칭 플랫폼업
7. 광고·마케팅 대행 및 플랫폼 내 광고 서비스업
8. 지식재산권(특허·상표·저작권·데이터셋)의 취득·관리·라이선싱 및 기술이전업
9. 위 각 호에 부수하는 일체의 사업

> (실제 등기 시 표준산업분류·업종코드 매핑은 법무사 확인.)

## 3. 개발·혁신 헌장 (핵심 — 상시 준수)

> **원칙: 기능을 개발·개혁·혁신할 때는, 만들기 전에 반드시 아래 2가지를 먼저 검토한다.**

### 3-1. 기능 개발 4단계 게이트
모든 신규/변경 기능은 다음 순서를 거친다.

1. **[특허화 게이트] 우리가 특허 낼 수 있는가?**
   - 신규성(기존에 없던 방식인가)·진보성(당업자가 쉽게 못 떠올리는가)·산업상 이용가능성을 자체 점검.
   - "낼 만하다" 판정 시 → **공개(출시·논문·발표) 전에** 우선일을 잡는다(가출원 또는 본출원). 공개 후엔 자국 신규성 상실 → 권리화 곤란.
2. **[침해 게이트 / FTO] 남의 특허를 침해하지 않는가?**
   - KIPRIS(특허정보넷)·Google Patents에서 유사 선행기술·등록특허를 검색.
   - 겹치면: 설계우회(청구항을 피하는 구현) / 라이선스 / 무효자료 확보 중 택일.
   - 결론이 애매하면 **변리사 FTO 검토** 후 진행.
3. **[개인정보·법령 게이트] 사용자 데이터가 어디로 가는가?** ← 2026-08-26 신설
   - 이 기능이 **사용자 데이터를 외부(자사 서버 밖)로 보내는가?** 보낸다면 아래를 **코드 짜기 전에** 끝낸다.
     - a. `tools/outbound-allowlist.json` 에 **호스트·수탁자·나가는 항목·방침 근거 조항**을 등재한다.
     - b. 근거 조항이 없으면 **개인정보처리방침·약관을 먼저 고친다.** 코드가 문서를 앞서가면 안 된다.
     - c. 국외 업체면 **국외이전 고지**(개인정보보호법 제28조의8)까지 확인. 위탁은 제26조.
     - d. **끄는 스위치를 같이 만든다.** 서버 환경변수 게이트(예: `RECEIPT_VISION_ENABLED`)를
          기능과 **동시에** 만든다. 나중에 붙이면 사고 났을 때 못 끈다.
     - e. 앱이 외부로 **직접** 보내는 구조는 피한다. 서버를 경유시켜야 kill-switch가 듣는다.
          (Cloudinary 업로드가 앱→외부 직행이라 서버로 못 막았다. 그 대가를 겪었다.)
   - **판단이 애매하면 만들지 말고 먼저 묻는다.** "일단 만들고 방침은 나중에"는 금지.
   - 배포 전 `node tools/check-outbound.js --strict` 와 `node tools/check-secrets.js` 가 통과해야 한다.
4. **[구현] 위 1~3 통과분만 개발**하고, 특허화 대상은 별도 아이디어 노트에 즉시 기록(발명일·발명자·구성 요약).

### 3-2. 운영 규칙
- **개발 로그에 IP 태그**: 각 기능 커밋/문서에 `[특허후보]` 또는 `[FTO확인]` 표기.
- **분기 1회 IP 정리**: 특허후보 모아 변리사와 출원 여부 결정.
- **공개 전 검토 필수**: 출시·전시·지원사업 발표 자료에 미출원 신기술을 노출하지 않는다.
- **Claude(개발 보조)의 책무**: 새 기능 제안·구현 시 (a) 특허 가능성 한 줄 코멘트, (b) 명백한 선행기술/침해 우려가 보이면 경고를 **먼저** 제시한다. (변리사 대체 아님, 1차 스크리닝.)

## 4. 특허(IP) 전략 로드맵

- **현재 상태**: 12개 발명이 담긴 **가출원(임시명세서)** 완료 → 우선일 확보됨.
- **최우선 (마감 있음)**: 가출원일로부터 **12개월 내 정식 본출원**(청구범위 포함)으로 전환. 미전환 시 우선권 소멸.
- **신규 발명 추가 출원** (가출원 이후 개발분, 현재 보호 밖):
  - 디지털 명함 + 반강제 연락처 저장(vCard QR) 단골 확보 → **독립 발명, 우선순위 높음**
  - 서버에서 파싱규칙을 내려받아 이종 앱 화면을 무중단 학습·개선하는 방법
  - **[특허후보·강함] 스샷 크라우드-교정 자가진화 파서**: 오픈톡방 등 이종 콜 스샷을 OCR → 기사가 출발지/목적지를 교정 → (원본 OCR ↔ 교정값) 쌍을 서버에 축적 → 그 말뭉치로 파싱규칙을 학습·개선해 기기로 재배포 → 인식·추출 정확도가 사용할수록 실제 상승. 이를 기사 운행데이터+이벤트와 결합해 시외·귀로 수요 포인트를 예측. (OCR 자체는 신규성 없음 — **크라우드 교정 루프 + 자가진화 파싱 + 수요예측 결합**이 신규성/진보성 포인트. FTO: 영수증·문서 OCR 특허 광범위하므로 청구항은 "택시 이종콜 스샷 교정-학습-수요예측 결합"으로 좁혀 변리사 검토.)
  - 이벤트(야구·콘서트·크루즈·리조트) 기반 택시 수요 예측 피드
  - GPS 지역·시내외·심야 tiered 미터 + 플로팅 백그라운드 실시간 요금
  - 야간기사 영업일(dayStart) 정규화
  - → 본출원에 포함하거나 추가 가출원으로 우선일 확보.
- **해외**: 필요 시 12개월 내 PCT.
- **상표**: "콜레이더/CallRadar"(견본 보유) 특허와 별개로 출원·등록.

## 5. 지원사업 로드맵 (내년 초 목표)

정체성(모빌리티 데이터/핀테크)에 **정확히 맞는 것만** 노린다.

- **예비창업패키지** (사업자등록 전 / 아이디어~기획) — 정석 진입점, 사업화 자금 + 멘토링.
- **초기창업패키지 / 초격차(미래모빌리티·빅데이터)** — 법인·초기 단계로 넘어가면.
- **TIPS·딥테크 TIPS** — 법인 + 민간투자 유치 전제, 로드맵에 예약.
- **규제 체크(필수)**: 개인 위치·운행정보 취급 → 「위치정보법」상 위치기반서비스사업 신고 여부 확인, 애매하면 ICT 규제샌드박스.
- (참고: KISA 안전LBS공모전·국방벤처는 정체성과 어긋나므로 후순위.)

> 다음 작업: 위 후보를 **마감일·자격요건·지원규모·신청링크**로 추린 트래커 + 예비창업패키지용 사업계획서 초안.

## 6. "진화하는 앱" 운영 원칙

- 실사용자(택시 기사) 피드백 → 즉시 기능화 → **사람처럼 전수 검증(온디바이스)** → 배포. "됐다" 대신 **근거로 확인 후** 종료.
- 근거 없는 수치·편법 금지(예: 확인 안 된 할증률 하드코딩 금지).
- 모든 신기능은 3장 게이트(특허·FTO)를 통과.
- 대표(사람)가 방향·판단을 이끌고, Claude는 그 방향을 **빠르게 구현·검증·문서화**하며 IP 1차 스크리닝을 보조한다. 학습이 쌓일수록 제안의 질을 높인다.

## 8. 아키텍처 원칙 — 모듈러 · 자동연동 · 튜닝모드 (대표 방향)

> 대표 지시: "기능들이 각자 따로 작동하다가 모으면 자동으로 합쳐지고 연동되게. 매번 노가다 말고 AI로. 무한히 기능이 늘어도 앱이 자동 연동·자동 복구되게." → 이걸 **정직하게(구라 없이) 실현 가능한 범위**로 규정한다.

### 8-1. 실현 가능한 것 (지금부터 이 구조로 만든다)
- **모듈(카드) 아키텍처**: 모든 기능 = 표준 인터페이스를 가진 독립 모듈(id, 제목, 데이터소스, 화면조각, 설정). 새 기능 추가 = 화면마다 배선하는 게 아니라 **모듈 등록** 한 번. → 노가다 감소, 확장성 확보.
- **공용 신호 버스(데이터 허브)**: 모듈은 공통 신호(운행기록·위치·시간·이벤트·정산)를 구독/발행한다. 점대점 배선 없이 **모아지면 자동으로 서로 연동**됨(예: 이벤트 모듈 + 운행 모듈 → 수요 카드).
- **서버 주도 레지스트리**: 서버가 "사용 가능한 모듈·규칙 목록"을 내려주고 앱이 동적 렌더. (이미 있는 '규칙 다운로드 서버→앱'의 확장.) → **앱 업데이트 없이 기능 on/off·배포** 가능.
- **튜닝 모드와 결합**: 기본 모드 = 우리가 정한 배치. 튜닝 모드 = 기사가 **모든 기능·소탭·작은 기능까지 바로가기 모듈로 홈에 끌어와 바둑판처럼 꾸미기**. 모듈 아키텍처가 곧 튜닝모드의 토대. (튜닝모드는 UI 재설계 안정화 후 착수.)
- **정직한 "자동 복구" = 장애 격리**: 한 모듈이 죽어도 **앱 전체가 죽지 않게**(모듈 단위 try/catch·"일시 오류" 표시), 서버에서 문제 모듈 **원격 비활성(kill-switch)**, 오류 원격 수집(telemetry). → "무한히 기능이 늘어도 앱은 안 죽는다"의 실제 구현.
- **AI 조합 층**: AI(추후 Claude API/온디바이스)는 코드를 스스로 짜는 게 아니라, 공용 버스의 데이터를 **읽어 모듈 간 인사이트를 조합**(예: "지금 이 이벤트+내 운행패턴 → 이동 추천"). 운행데이터가 쌓여야 활성(개인비서 게이트).

### 8-2. 정직 경계 (구라 금지 — 안 되는 것은 안 된다고 명시)
- **완전 자율 자가작성·자가수리 앱(사람 개입 0)은 현재 기술로 불가.** 그렇게 광고/약속하지 않는다.
- 없는 기능(실시간 콜지도·AI핫존·포인트 등)을 **있는 것처럼 UI에 쓰지 않는다.** "준비 중/데이터 모으는 중"이면 그대로 정직하게 표기.
- 데이터가 없으면 가짜 수치·가짜 지도 금지. 참여 유도는 **실제 상호가치**로만(내 기록이 익명으로 수요지도를 만들고 나도 남의 지도를 본다 — 데이터가 실제로 쌓인 뒤 공개).

> 다음 작업(아키텍처): 모듈 표준 인터페이스 정의 → 홈 카드부터 모듈화(오늘매출/월급/이벤트/근무세션) → 서버 레지스트리 연결 → 장애 격리 래퍼 → 튜닝모드.

### 8-3. AI 운행 비서 — 진화 모델 (핵심 IP·수익화 축)
- **데이터 결합**: ① 기사 스스로 남기는 운행 데이터 + ② 제보 데이터(시외·귀로콜)를 **합·평균**내어, "귀로/시외콜이 잘 잡히는 포인트·시간대"를 알려준다. 여기에 ③ **이벤트(행사·공연·축제 지역)**를 더하면 예측이 점점 정교해지는 **진화형 비서**가 된다.
- **자기강화 루프**: 기사는 자기 이득 때문에 시외/귀로 기록을 정확히 남길 수밖에 없고 → 데이터가 쌓일수록 비서가 똑똑해지고 → 더 쓰게 되는 선순환. (억지 유도 X, 실제 가치 O — 구라 없이.)
- **활성 게이트**: 데이터가 충분해질 때까지는 "준비 중"으로 정직하게 표기. 개인 기록은 그 전에도 즉시 가치.

### 8-4. 수익화 — 무료 체험 → 구독 전환 (대표 지시)
- **개발·초기 단계: 전면 무료.** (사용자·데이터 확보 우선.)
- **정식 서비스 후**: 신규 가입자는 **최초 신청 시 1개월 무료 체험**.
- **전환 설계**: 체험 기간에 비서·수요예측의 **편안함에 익숙해지게** 만들고, 체험 종료 시 **유료 구독형**으로 전환. "이거 없으면 불편하네 → 구독" 심리를 노린다.
- **정직 가드레일(필수)**: 습관화는 **실제 가치**로만 만든다. 해지 방해·숨은 과금·기만적 다크패턴 금지(구라 없게 원칙과 동일). 무료/유료 경계, 해지 방법, 요금은 항상 명확히 고지.
- 구현 예약: 체험 만료 D-day 카운트 + 구독 상태 플래그(서버) + 유료 기능 게이트. (정식 서비스 단계에서.)

### 8-5. 단계적 중독화 = 수익화 엔진 (핵심 원칙 · 대표 지시)
> "킬러 기능이 아무리 많아져도, **스며드는 중독화 과정**이 있어야 앱이 수익화된다." — 대표
- **2단계 데이터 사다리**: (1) **개인 데이터 → 나만의 비서**(내 운행 리듬 등, Day-1 가치) → (2) **전체 유저 통합 데이터 → 더 풍부한 정보**(전체 기사 시간대·지역 수요, 유저 늘수록 세분화). 개인가치로 붙잡고, 집단가치로 못 떠나게.
- 각 기능은 "한 번 써보면 → 편해서 계속 → 없으면 불편 → 구독"의 흐름에 기여해야 한다. 단발성 기능 나열 금지.
- **비식별 원칙**: 전체집계는 개별 행/user_id 노출 없이 집계만(정관 1·3장). 신뢰가 곧 잔존율.
- **Claude(대표 대행)의 상시 의무**: 앞으로 모든 기능을 개발·제안할 때 **"이게 중독화(개인→집단 사다리, 재방문·습관)에 기여하는가?"를 먼저 자문**하고, 기여할 수 있으면 **대표에게 먼저 역제안**한다. 대표만 아이디어 내게 두지 않는다.

### 8-6. 정밀도 계층 유료화 (대표 지시)
- **원칙**: 무료 = **동/구 단위**(대략적 수요), 유료로 올라갈수록 **위치·건물명이 더 정확**하게. "더 정확한 위치가 곧 돈"이므로 정밀도 자체가 구독 가치.
- **구현 상태**: 서버 `/api/demand?precision=coarse|fine` 완료(coarse=동/구로 뭉침[무료 기본], fine=원본 최상세[유료]). 인젝션 방지 상수 매핑.
- **단계형(정직)**: "건물명 수준"은 GPS 좌표 **역지오코딩(카카오 로컬 API)** 이 붙고 데이터가 쌓여야 완성 → 유저 늘수록 정교. 현재 fine=입력된 최상세 위치. 없는 정밀도를 있는 척하지 않는다.
- **게이팅**: 실제 무료/유료 분기는 구독 플래그(8-4)와 연결 — 정식 서비스 단계. 지금은 서버 능력만 선반영("미리 해놓기").
- **계층 예시**: 무료 "강남구" → 유료 "강남구 역삼동" → 상위 유료 "역삼동 ○○빌딩/○○역 3번출구"(역지오코딩 후).
- **데이터 집약 효과(대표 통찰)**: 유저·트립이 쌓일수록 특정 목적/출발(예: **인천공항행 손님이 자주 나오는 건물·호텔·지점**)이 **클러스터로 집약**된다. 무료는 "이 구 근처 공항손님 많음", 유료 AI는 "**○○호텔·△△역 3번출구에서 공항행 콜 자주 발생**"까지 짚어준다 → 정밀 위치가 곧 구독 가치. 공항 승객예고(시간)와 결합하면 "몇 시, 어디서 공항손님"이 완성.

## 8-7. 무료→유료 전환 · 반감 방지 공지 정책 (대표 지시)
> "킬러 기능은 베타 → 무료 → 유료 전환. 그때 유저 반감 안 사게 표현·공지를 미리 해둔다."
- **반감 방지 3원칙 (핵심)**:
  1. **뺏지 않는다**: 지금 무료로 쓰던 건 계속 무료(예: 동/구 단위 수요, 개인 리듬, 기본 기록). 유료화는 **새 고급 기능만**(정밀 위치·GPS 자동 귀로콜 레이더·건물명 등). 있던 걸 유료로 잠그면 반감 최대 → 금지.
  2. **얼리버드 보상**: 베타·초기 참여 기사에게 **정식 출시 후 혜택**(장기 할인 또는 특정 고급기능 무료 유지). 초기 데이터 기여자 우대 → 충성도.
  3. **미리·투명하게 공지**: "베타·무료 중 / 정식 출시 후 일부 고급기능은 구독 전환 예정"을 **처음부터** 표기. 요금·무료 경계·전환 시점 명확히. 다크패턴·기습 과금 금지(8-4·구라 없게).
- **표기 라벨**: 고급 후보 기능에 "베타 · 무료" + "정식 출시 후 구독 전환 예정" 안내. 무료 유지 기능엔 안 붙임.
- **공지 문구(초안)**: "콜레이더는 지금 **베타**라 모든 기능이 **무료**입니다. 정식 출시 후에는 **정밀 위치·귀로콜 자동감지 같은 일부 고급 기능**만 구독으로 전환될 예정이에요. 지금 쓰시는 기본 기능(수익 기록·동단위 수요·개인 리듬)은 **계속 무료**입니다. **베타에 함께해 주신 기사님께는 정식 출시 때 감사 혜택**을 드립니다. 🙏"

## 8-8. 기능 온/오프 기본 원칙 (대표 지시)
- **모든 사용자향 기능/카드는 온·오프 토글을 기본 제공**한다. 기사마다 원하는 것만 켜서 쓰게(불필요한 건 끄게). 강제 노출 금지.
- 토글은 **기능 등록소(FeatureRegistry)** / 설정에 모으고, prefs로 저장(기본값은 유용한 쪽으로). 이는 8-2 튜닝 모드(홈 꾸미기)의 토대이기도 하다.
- 신규 기능 개발 시 **온/오프부터 설계**한다(사후 추가 아님).

### 9-1. 코드/아키텍처 실수
- **[중대] 엔드포인트 오배선**: 제보·수동 저장은 **반드시 `POST /api/trips/manual`** 로 보낸다. `/api/trips`(간단 핸들러)는 `is_report·payment_type·source·raw_ocr`를 **무시**한다. 새 저장 코드 작성 시 어느 핸들러가 어떤 필드를 저장하는지 **서버 코드부터 확인**. (2026-07-27: AI 비서 제보가 `/api/trips`로 가서 raw_ocr 미저장 → 30분 허비. 단서는 `is_report=false` 응답.)
- **성급한 원인 단정 금지**: "배포 안 됨 = Render 지연"으로 지레짐작했으나 실제는 내 엔드포인트 실수. **증거(대시보드 Live 커밋, 응답 전체 필드)로 확인 후** 결론. 여러 번 재시도로 시간 허비 말 것.
- **구라(없는 기능 있는 척) 금지**: 제보 탭에 "실시간 콜지도·AI 핫존·포인트 배지" 등 미구현 기능을 있는 것처럼 넣었던 것 삭제. 준비 중이면 "준비 중"으로 정직 표기.

### 9-1b. 릴리스·심사(Play) 관리 원칙 (대표 지시 · 필수)
- **심사 트리거 기능은 별도 '심사 차수'로 분리.** 민감권한(예: `ACCESS_BACKGROUND_LOCATION` 백그라운드 위치, 지오펜스 상시추적, 접근성, 알림 등 Play 심사 유발)이 필요한 기능은 **평상시 업데이트에 섞지 말고**, 날을 잡아 **한 번에 모아 제출**한다("한 번에 넘어가게").
- 평상시 업데이트 = **심사 안 걸리는 것만**(권한 불변, 서버·UI·온디바이스 기능). 그래야 배포가 빠르고 리스크 없음.
- **v18 심사중**에는 그 위에 심사 트리거를 얹지 않는다. (이번 세션: 음성 TTS·갤러리 OCR·텍스트 검색·네트워크만 → 새 민감권한 0, 심사 무관.)
- 심사 필요 묶음(예약): GPS 자동감지·지오펜스 귀로콜 레이더(A-3/B-1 자동판), 자동 운행기록(백그라운드 위치) 등 → **전용 심사 차수**로.
- **심사 차수 실행 시점(대표 지시)**: **v19가 안정되어 버그가 적을 때** 민감권한 묶음을 모아 한 번에 심사. 그 전까진 심사 무관 기능만 업데이트.
- (역제안 채택) 심사 차수엔 GPS 자동 귀로콜 레이더 + 자동 운행기록 + 백그라운드 미터 + 카카오 로컬 API(역지오코딩)를 **한 묶음**으로 올려 심사를 한 번만 겪는다.

### 9-2. 빌드/배포/도구 실수
- **서버 배포 리포 혼동**: 서버 push는 `C:\CallRadar\server`에서만(remote 있음). `C:\CallRadar`엔 remote 없음 → push 실패. (7-1 참조.)

### 9-4. 개인정보·보안 사고 (2026-08-26 — 가장 무거운 실수)

> 대표: "여러 번 코드에 문제 없냐 하고 나한테 물으면서 콜레이더 만들었다."
> 그 질문에 확인 없이 "문제 없다"고 답해 왔다. 아래는 그동안 실제로 있던 것들이다.

- **[중대] 코드가 방침을 앞서갔다.** 영수증 사진이 **Cloudinary(미국)에 업로드되고 그 URL을 Anthropic(미국)이 가져가 판독**하고 있었는데, `privacy-policy.html` 제5조 수탁자 표에는 **Render·카카오 둘뿐**이었고 제4조에는 **"제3자에게 제공하지 않습니다"**라고 적혀 있었다. 국외이전 조항(제28조의8)은 아예 없었다. 몇 주간 두 스토어에 배포된 상태였다.
  → 조치: `/api/ai/receipt-vision`·`/api/ocr/ledger` 서버 게이트로 **중지**(기본 OFF). 3-1 게이트에 개인정보·법령 관문 신설. `tools/check-outbound.js` 로 기계 검사.
- **[중대] kill-switch를 만들지 않고 기능을 냈다.** Cloudinary 업로드는 **앱이 외부로 직행**하는 구조라 서버에서 못 막는다. 끄려면 Cloudinary 콘솔에서 preset을 꺼야 한다. **외부 전송은 반드시 서버 경유**로 만들어야 원격으로 끌 수 있다.
- **[중대] 업로드한 사진의 파기 로직이 없다.** 방침엔 "탈퇴 후 30일 내 파기"인데 Cloudinary 원본은 영구히 남는다. **unsigned preset이라 URL만 알면 누구나 열람 가능.** 문서와 실제가 불일치.
- **[보안] 자사 세션 토큰이 외부 API로 나갔다.** `AirportScreen.kt` 번역 호출이 `api.mymemory.translated.net` 에 **우리 Bearer 토큰을 붙여** 보내고 있었다. 자사 서버 호출 코드를 복사하면서 딸려온 것. 다른 제3자 호출엔 토큰 제거 방어가 있었는데 거기만 빠졌다.
  → 조치: 제거. `tools/check-secrets.js` 가 이 패턴을 상시 검사.
- **[보안] API 키 하드코딩.** `server/tolls.js` 에 `process.env.EX_API_KEY || '실제키'` 폴백이 박혀 있었다. **정관 7-1을 정관 안에 써놓고 코드에서 어겼다.** git 이력에 영구히 남는다.
  → 조치: 제거 + 키 없으면 기능만 조용히 꺼지게. 검사기가 이 패턴을 잡는다.
- **[누락] 위치 약관에 카카오가 없다.** 역지오코딩은 **카카오(`dapi.kakao.com`)가 1차**인데 `location-terms.html` 에는 Nominatim만 적혀 있다.
- **[검토필요] 승객 위치.** 예약 페이지 `/book/:userId` 에서 **승객 브라우저가 Nominatim을 직접 호출**한다. 승객은 앱 이용자가 아니라 동의 절차가 없다.

**여기서 뽑은 규칙 (재발 방지 — 반드시 지킨다)**
1. **"문제 없다"는 확인한 것만.** 검사기를 돌리고 그 출력으로 답한다. 안 돌려봤으면 "모른다"고 한다.
2. **외부 전송 코드는 방침 수정과 같은 커밋에.** 코드가 문서보다 먼저 나가면 그 순간 위반이다.
3. **끄는 스위치를 기능과 동시에.** 나중에 붙이면 사고 났을 때 못 끈다.
4. **외부 전송은 서버 경유.** 앱→외부 직행은 원격으로 못 막는다.
5. **법령에 걸리면 일단 멈춘다.** (대표 지시) 고쳐서 계속 가는 게 아니라, 멈추고 정리한 뒤 다시 켠다.
6. **새 기능이 데이터를 밖으로 보내면 만들기 전에 묻는다.** "일단 만들고 방침은 나중에"는 금지.

### 9-5. 사진·개인데이터 처리 설계 원칙 (2026-08-27 신설)

> 대표: "이 기능을 보안할 방법을 생각하고 만들어라 다시."
> 기능을 지우는 게 답이 아니다. **안전한 구조로 다시 만드는 것**이 답이다.

**계층 순서 — 위에서부터 시도하고, 안 되면 한 칸씩 내려간다.**

| 층 | 방식 | 고지 필요 | 언제 쓰나 |
|---|---|---|---|
| 1 | **폰 안에서만 처리** (ML Kit 등) | 없음 | 기본값. 대부분 여기서 끝난다 |
| 2 | 자사 서버로 보내 처리 후 **즉시 폐기** | 위탁(호스팅) | 폰이 못 하는 계산 |
| 3 | 자사 서버에 **인증 접근·암호화·기한부** 보관 | 위탁 + 보유기간 | 증빙으로 남겨야 할 때 |
| 4 | 제3자 API 경유 (**자사 서버를 통해서만**) | 위탁 + 국외이전 | 다른 방법이 없을 때만 |

- **앱 → 외부 직행 금지.** 반드시 자사 서버를 거친다. 그래야 원격으로 끌 수 있다.
- **공개 URL 금지.** 보관하면 인증된 본인만 열 수 있어야 한다(unsigned·비밀주소 방식 금지).
- **보관하면 기한을 함께 정한다.** 자동 파기 코드를 기능과 같이 만든다.
- **kill-switch 를 기능과 동시에** 만든다(환경변수 게이트).

**교훈 — "AI 아니면 못 푼다"는 대개 틀리다.**
장부 사진에서 날짜·금액 짝짓기가 안 맞자 "표 구조는 비전 모델이라야 풀린다"고 판단해
사진을 국외로 보내는 설계를 만들었다. **틀렸다.** ML Kit 은 글자마다 좌표(boundingBox)를
같이 주는데 우리 파서가 `.text` 로 납작하게 만들어 그 정보를 버리고 있었다.
좌표를 쓰니 폰 안에서 풀렸다(`OcrLayout`·`LedgerGrid`).
→ **데이터를 밖으로 내보내는 설계를 떠올렸으면, 먼저 "지금 가진 정보를 다 쓰고 있나"를 확인한다.**

## 10. 자기진화 AI 로드맵 (대표 비전 — 핵심)
> "AI는 개별 작동 + 유저데이터 통합 두 레벨로, 스스로 학습·진화. 데이터·사용이 많을수록 똑똑해지고, 그 학습이 역으로 보고서로 우리에게 와서 유저가 말 안 한 기능을 발전시킨다. 일/주/월 브리핑 + PDF. 오류·기능·습성을(개인정보 제외) 앱이 스스로 진화 재료로."

### 10-1. 2레벨 AI (무료/유료 = 데이터 레벨 차이)
- **개별 데이터 AI (무료)**: 내 운행 리듬·기록 기반 개인 비서(Day-1 가치). 이미 구현(리듬·개인 순수익).
- **유저 통합 AI (유료)**: 전체 기사 비식별 집계 + 정밀 위치(8-6). 유저·사용 늘수록 세분·정확 → 구독 가치. 이미 골격(/api/demand, 정밀도 계층).
- 두 레벨의 **데이터 품질 차이 = 과금 근거**. 무료는 동/구·개인, 유료는 건물·집단.

### 10-2. 자기진화 텔레메트리 → 내부 보고서 (핵심 신규)
- 앱이 **비식별**(개인정보 제외)로 **오류 로그·기능 사용빈도·행동패턴**(어떤 화면 많이 쓰나, 어디서 이탈하나, 어떤 요청 많나)을 서버에 전송 → 집계.
- 서버가 **주간 내부 리포트**(대표+Claude용)로 정리: "이번 주 최다 사용 기능 / 오류 급증 지점 / 유저가 자주 시도하다 실패한 동작(=숨은 니즈)".
- → 유저가 **말하지 않은 기능**을 데이터로 발견해 개발 우선순위화. "역으로 보고서가 우리에게"의 실현.
- **정직·프라이버시**: 개인 식별정보 절대 미수집, 집계·익명만. 수집 항목 앱 내 고지 + 옵트아웃(온/오프 원칙 8-8).

### 10-3. 일/주/월 브리핑 + PDF
- **일간**(현재 브리핑 확장) / **주간**(요일별 매출·최고시간·수요 요약) / **월간**(월 순수익·리듬·세무용 요약).
- 유저가 원하면 **PDF 다운로드**(세무·정산·자기점검용). 문서 생성으로 구현.
- **글짓기 품질**: 1차 = 잘 설계된 템플릿+데이터(준전문). 2차 = **Claude API 연동 시 진짜 전문 문장**(비용/키 필요 → 유료 티어 가치와 결합).

### 10-4. "비서가 뭔지" 온보딩
- 데이터 분석 결과로 "당신의 비서는 이런 걸 해줍니다"를 **실제 내 숫자로** 보여주는 설명(빈 껍데기 X, 내 리듬·수요로 즉시 시연).

### 10-5. 정직 경계 (구라 금지)
- 사람 개입 0의 **자율 자가작성·자가수리**는 불가. "스스로 진화" = **데이터 집계 + 텔레메트리 리포트 + (추후)LLM 조합**으로 실현하며 그렇게만 설명한다.

### 10-6. Self-Evolve Engine — 도메인 독립 재사용 IP (별도 제품/스핀아웃)
> 대표 지시: "자기진화 루프를 콜레이더에만 두지 말고, 다른 종목 앱/프로그램에 꽂을 수 있는 **별도 프로그램**으로. 예: 주식(특정 유튜버·세력주 데이터/영상 분석 자기진화), 실버앱(노인 전문) 등. 인간이 필요로 하는 걸 스스로 찾아내는 엔진."
- **정의**: 도메인에 무관한 **자기진화 니즈발굴 엔진** = (a) 익명 사용/행동/결과 이벤트 수집 → (b) 집계 → (c) **실패·이탈·반복시도 = 미발화 니즈** 발굴 → (d) 내부 리포트 → (e) 개발 우선순위 자동화. 여기에 도메인별 **애널라이저 플러그인**(예: 주식 영상 분석, 노인 행동 분석)을 얹는다.
- **재사용 산출물(SDK)**: `C:\CallRadar\selfevolve_sdk\` — 서버(Node/Express, `domain` 컬럼으로 여러 종목 1DB), 앱(Android/Kotlin 클라이언트), 컴퓨터/웹(브라우저 JS 클라이언트), README(주식·실버 적용 예시). 콜레이더에서 검증된 루프를 그대로 일반화.
- **도메인 예시**: 주식앱=유튜버/세력주 시그널·유저반응 수집→"자주 보지만 실행 못 한 신호=니즈"; 실버앱=노인 사용패턴·실패지점 수집→"노인이 원하나 못 쓴 기능" 발굴.
- **정직 경계**: 엔진은 *수집·집계·니즈발굴*을 자동화(진짜 진화). "영상 분석"·"자가 코드작성"은 도메인 플러그인/추후 LLM 몫이며 엔진이 스스로 코드를 쓰는 건 아니다.
- **[특허후보·별도]**: 도메인 독립 "미발화 니즈 발굴 자기진화 루프" 프레임워크 — 콜레이더 출원과 별개로 상위(포괄) 청구 검토. 변리사 논의.

### 10-7. 특허 검증 결과 (정직 — 1차 스크리닝)
> ⚠️ **일반형 텔레메트리→실패/이탈→니즈발굴→우선순위 루프는 그 자체로는 신규성이 약하다.** 선행기술 광범위:
- US7552365 — 사용자 활동에서 실패 이벤트 감지 + 피드백 요청
- US9979675B2 — 텔레메트리 이상탐지 / churn·행동로그 기반 기능 우선순위화는 업계 표준(AWS 문서 포함)
- **결론**: "독립 신기술"로 단정하면 구라. 일반 루프 단독 출원은 비권장(거절 위험·변리사 비용 낭비). **가치는 특허가 아니라 제품 해자(누적데이터·잔존율).**
- **특허 내려면**: 진짜 새로운 결합이 필요 → 콜레이더의 강한후보(**이종 콜 스샷 크라우드-교정 자가진화 파서 + 수요예측**, 4장·9장)에 텔레메트리를 얹어 청구범위를 좁힌 결합으로. 변리사 FTO로 확정.

- 콜레이더 이후 **주식 프로그램**(봉선추양사부 버전) 예정. **Self-Evolve Engine(10-6) + 주식 도메인 애널라이저**(유튜버/세력주 시그널·유저반응·영상 분석) + @추가 기술 필요.
- 미리 설계: 엔진은 수집·집계·니즈발굴 담당, 주식 특화(영상 파싱·시그널 추출·백테스트)는 도메인 플러그인. Self-Evolve SDK를 그대로 재사용해 개발 단축.

## 11. 튜닝 모드 — 홈 자유 꾸미기 상세 스펙 (UI 재설계 최종형 · 대표 지시)
> "삼성 One UI 편집모드처럼 **모든 메뉴 + 하위 탭까지** 블록으로 홈에 끌어와 바둑판으로 배치·꾸미기. 기능등록소 온오프를 넘어 자유 배치."
- **블록 레지스트리(핵심)**: 앱의 **모든 진입점**(홈 카드·기록 하위탭[내역/달력/지출/월급]·공항 하위탭[입출국장/도착/혼잡도]·더보기 모든 메뉴·AI 비서 항목 등)을 **블록 정의**(id, 아이콘, 라벨, 목적지)로 등록. 이 목록에서 홈에 얹을 수 있게.
- **편집 모드(그림 참조)**: 홈 우상단 "꾸미기" → 편집모드 진입 → 블록 **추가/삭제/드래그 재배치**(2열 바둑판 그리드) → 저장. 기본 모드=우리 배치, 튜닝 모드=기사 맘대로.
- **레이아웃 저장**: prefs(JSON: 블록 id 순서·크기)로 저장·복원. 프리셋(심플/기본/정보형)은 이 레이아웃의 기성품.
- **구현 슬라이스(순서)**: (1) 블록 레지스트리 데이터모델 + 모든 메뉴/하위탭 등록 → (2) 홈이 레이아웃(prefs)대로 블록 렌더 → (3) 편집모드(추가/삭제) → (4) 드래그 재배치 → (5) 목업 하단 액션바(+운행추가/사진가져오기/기록분석/근무시작)까지 블록화.
- **정직 경계**: 큰 작업 → 슬라이스마다 빌드·검증. 한 번에 안 함(반쯤 만들다 멈춤 금지, 9장).
- (진행) 홈 하단 바로가기 바 = 튜닝 홈 1단계 완료(가져오기/기록/공항/명함/더보기 · 온오프 home_shortcuts).

## 11-1. 이벤트 파장 예측 알림 (진짜 킬러 — 대표 지시)
> "공연·행사 리스트 + 현재시각으로 **시작→파장(끝) 시간을 예측·분석**해, 사람 나올 시간에 기사를 보내거나 알림. 이벤트가 앱에서 찾기 힘드니 리스트도 간단·눈에 띄게."
- **파장 예측**: 이벤트 start_at + 유형별 소요(공연≈2.5h, 스포츠≈3h, 축제=종료시각) → **파장 예상 시각**. 그 지역 콜 폭증 타이밍.
- **알림**: 파장 30~60분 전 로컬 알림 "○○(장소) 곧 파장 · 그 근처 콜↑ · 지금 이동 N분". (POST_NOTIFICATIONS 권한 — 경미, 심사 영향 확인.)
- **리스트 개선**: 홈/이벤트 화면에 **시간순 정렬 + 파장 예상 + 좌석수(규모)** 간단 표기. 찾기 쉽게 상단 노출.
- **데이터**: KOPIS(공연)·TourAPI(축제) start_at 있음. 좌석수·정확 종료는 있으면 사용, 없으면 추정(근거 표기, 구라 없이). 스포츠·크루즈는 별도 종료 추정.
- 구현 순서: (1) 이벤트에 파장 예상 시각 표기 → (2) 시간순 리스트 정렬·규모 → (3) 파장 임박 로컬 알림.

## 12. 학습 corpus 수집 폴더 (대표 협업 — OCR/파서 진화용)
- 대표가 **컴퓨터 폴더 하나**에 실물 이미지 수집: 일일마감명세서·제보콜(채팅) 스샷·가스비 영수증·급여명세서 등.
- **용도**: (원본 이미지 → OCR → 올바른 값) **정답쌍 corpus**. 이걸로 서버 파싱규칙을 학습·개선하고, 최종엔 Claude API 파싱의 few-shot/평가셋으로. (raw_ocr는 앱에서 이미 서버에 축적 중 — 이 폴더는 정답 라벨.)
- **워크플로**: 폴더째 넘겨주시면 유형별 분류 → 각 유형 파서(마감/제보/가스/명세서) 개선·검증. 개인정보는 corpus에서 마스킹.
- **효과**: 채팅 스샷 인식율(현재 낮음)을 실데이터로 끌어올리는 자기진화의 연료.
