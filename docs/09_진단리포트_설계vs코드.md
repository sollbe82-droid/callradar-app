*작성 2026-07-21 · 설계헌장 "예스맨 금지"로 씀 · 정본 9문서 + 실제 코드(all_kotlin_code.txt 3089줄, server.js 180줄) 대조*

> 읽는 법: 🔴 치명(뼈대가 흔들림) · 🟠 중요(곧 막힘) · 🟡 정리(문서·표기).
> 좋은 소식 먼저: **설계 문서들은 서로 잘 맞물려 있다.** 진짜 문제는 **설계 ↔ 현재 코드의 간극**이다.

## A. 한 줄 요약
현재 앱은 **"서버=진실 · 불변·추가형 · 멱등"** 이라는 설계의 3대 전제 위에 **서 있지 않다.**
지금 코드는 그 반대(서버가 id 발급 · 운행 수정/삭제 · 멱등 없음 · 로컬캐시 없음)로 돌아간다.
그래서 v10 최우선인 **4-1 전표금액 매칭은 "기능 추가"가 아니라 "뼈대 이설(移設)" 위에서만 가능**하다.

---

## B. 🔴 치명 — 정본 서버가 저장소 밖에 있다
- 연결된 `C:\CallRadarServer\server.js`는 **메모리 임시 토이**다: 엔드포인트가 `/v1/trips`·`/v1/users/register`·`/v1/hotspots`·`/v1/ai/recommend`·`/v1/stats`, 저장은 `const trips = []`.
- 그런데 **실제 앱**(`MainActivity.kt`)이 부르는 서버는 `https://callradar-server.onrender.com`이고 API가 완전히 다르다:
  `/api/today` `/api/profile` `/api/trips`(GET/POST/PUT/DELETE) `/api/trips/manual` `/api/trips/{id}/fare` `/api/stats/daily|pattern|comparison|insights` `/api/spots/{id}/heatmap` `/api/users/{id}` `/api/ranking/individual|company|guild` `/api/guilds` `/api/receipts` `/api/address` `/api/geocode`.
- **즉, 진짜 프로덕션 서버 소스가 이 저장소에 없다.** `server.js`는 옛날 실험본.
- 왜 치명인가: 설계의 최상위 축이 "서버=진실"인데 **그 진실의 소스가 버전관리·백업 밖**이다(헌장 원칙 3 정면 위반). 게다가 **4-1 전표매칭은 서버측 매칭 로직**이라, 이 서버 없이는 v10 최우선을 한 줄도 못 짠다.
- 조치: 프로덕션 서버(onrender) 소스를 **폴더로 연결**하거나 저장소에 편입. **이게 v10의 진짜 0순위.**

---

## C. 🔴 치명 — 데이터 아키텍처가 설계와 정반대
설계(02 멀티소스 · 03 자가복구)의 전제 vs 현재 코드:

| 설계가 요구 | 현재 코드 | 증거 |
|---|---|---|
| 클라 생성 **UUID**(멱등) | 서버가 `id = Date.now()` 발급 | server.js:41 / 앱은 서버 id 사용 |
| **불변·추가형** 기여 | 운행 **PUT 수정** | `/api/trips/{id}` PUT (MainActivity:953) |
| **소프트삭제**(status·휴지통) | 운행 **DELETE 하드삭제** | `/api/trips/{id}` DELETE (MainActivity:978) |
| Trip = **기여들의 파생** | Trip = **flat 단일 레코드** | TripItem 데이터클래스 하나 |
| 투폰 **합집합 병합** | 병합 개념 없음(마지막 쓴 게 이김) | 멱등키·병합 코드 0 |

- `UUID`·`contribution`·`projection`·`tombstone`·`superseded` — **코드 전체 검색 결과 0건.** 기여 모델의 흔적이 없다.
- 이건 "아직 구현 안 함"이 아니라 **반대 방향으로 이미 구현돼 있음**이다. 그래서 자가복구·투폰·오삭제복구·4-1 재연결이 **전부 지금은 불가능**하고, 나중에 얹는 게 아니라 **밑을 갈아야** 한다.

---

## D. 🟠 중요 — "폰은 캐시"가 없다 (로컬 저장 계층 부재)
- `Room`·`Entity`·`Dao`·로컬 DB **검색 0건.** 저장은 `SharedPreferences`(user_id·닉네임·목표금액)뿐.
- 화면마다 서버 `/api/...`를 **실시간 fetch**한다(홈·기록·통계·캘린더·스팟). 서버가 죽거나 오프라인이면 **화면이 빈다.**
- 03 자가복구는 "서버=진실, **폰은 캐시**, 폰 깨져도 복구"를 말하지만, **폰에 캐시가 없어서** 오프라인 입력·투폰 오프라인 병합은 코드적 근거가 아직 없다.

---

## E. 🟠 중요 — 4-1(전표금액 매칭)의 현재 실체 = 매칭이 없음
- **영수증(전표) OCR**: `ReceiptScanActivity` → `POST /api/receipts`로 **따로** 저장. 운행에 자동 연결 안 함.
- **자동 금액 채움**: `NaviIntentReceiver`(접근성 서비스, 2086줄)가 화면에서 요금을 감지해 `PUT /api/trips/{id}/fare`로 **덮어씀**.
- 즉 지금은 (1) 전표는 운행과 무관하게 쌓이고, (2) 요금은 접근성이 덮어쓴다. 설계 4-1의 핵심인 **"늦게 온 전표를 올바른 GPS 운행에 후보매칭(1건 자동 / 다건 확인 / 0건 inbox)"은 미구현.**
- 그리고 덮어쓰기(`/fare`)는 **기여가 아니라 파괴적 갱신** → 유저 수동정정 보호(precedence 999)·재계산·되돌리기가 성립 안 함.

---

## F. 🟠 중요 — driver_type는 반쪽만 구현
- 코드: 프로필 다이얼로그에서 `driverTypeInput = "personal" | "corporate"` → `PUT /api/users/{id}` `driver_type` 문자열 저장(MainActivity:1649,1683).
- 설계(04): `'private' | 'corp'` + **능력 플래그 프로파일**(`hasQuota`·`fuelSettlement`·`submitReceipts`·`workTimeMode`·`taxMode`·`receiptArchive`). 코드는 driverType을 **안 보고 플래그를 봐야** 함.
- 현실: **플래그 0개, 카드 `minRole` 게이팅 0개.** 설계의 핵심 메커니즘(if 분기 폭발 방지)이 통째로 미구현.
- 게다가 **네이밍 불일치**: 코드 `personal/corporate` ↔ 설계 `private/corp`. 지금 확정 안 하면 나중에 마이그레이션 비용.
- 파급: 05 계약콜 정산(`minRole:'corp'`)·근무시간(`workTimeMode`)이 전부 이 프로파일에 의존 → **04가 먼저 코드로 서야** 05가 얹힌다.

## G. 🟡 정리 — 문서/현실 불일치 (단일 출처 구멍)
1. **로드맵이 ✅라는데 문서 실물이 없는 설계 3종:** `화면 등록소 뼈대 v2` · `근무시간·교대` · `온보딩·인앱설명(플로팅)`. 로드맵 §5 커버리지맵은 ✅ 완료로 표기하지만, **업로드된 정본 9문서에 이 셋의 문서가 없다.** → "설계 완료"가 문서로 증명 안 됨. (특히 등록소 v2는 아이디어 흡수·driver_type·계약콜이 전부 얹히는 뼈대인데 문서 부재.)
2. **문서에 없는 대형 기능이 앱에 있음:** **길드·랭킹(개인/회사/길드)·뱃지·레벨**(게이미피케이션)이 코드에 실재(`/api/guilds`·`/api/ranking/*`·badges·levelInfo)하는데, **어느 설계문서·로드맵에도 없다.** 방향(정체성: 조용한 실용 vs 게이미피케이션)과 충돌 가능 — 의도인지 확인 필요.
3. **로드맵 "v8 shipped"인데 이 코드 덤프엔 없는 것:** 예상월급 계산·매출 분리(현금/카드/플랫폼)·사납금. → 서버측이거나 **덤프가 부분적**(아래 H).

## H. 진단의 한계 (정직하게)
- `all_kotlin_code.txt`는 **8개 kt 파일뿐**(위치추적·도착TTS·네비접근성·영수증OCR·MainActivity·테마). income/급여/현금/경비 로직이 안 보임 → **전체 코드가 아니다**(부분 스냅샷). 서버측(onrender)은 아예 못 봄.
- 따라서 위 진단은 **"앱 클라이언트 + 토이 서버" 기준**이다. 급여·현금·사납금의 실제 구현은 서버/누락파일에 있을 수 있음. **B(서버 소스)·부분덤프 해소** 없이는 코드 진단이 절반이다.

## I. 설계 자체의 구멍 (문서 내부, 코드와 별개)
대체로 탄탄하지만 미결 4개:
1. **삭제 vs 불변·추가형의 근본 긴장**(03·07): tombstone은 append지만 PIPA/Play "백업까지 물리 파기"는 append-only를 깬다. "파기 로그"로 얼버무림 → **파기 절차 실무 상세 필요.**
2. **유형 전환 시 "기간별 profile 이력"(04 §5)과 projection 함수(02 §4)의 접점 미정의**: `projectTrip`이 시점 profile을 인자로 안 받음 → 과거를 그 시절 사납금 유무로 계산하는 경로가 설계에 안 이어짐.
3. **계약콜 월 귀속 vs 근무시간 영업일/교대 기준(05)**: 예상월급 역산이 "월 통 금액"과 "영업일 기준"을 어떻게 합치는지 미정.
4. **AI confidence 임계값 수치 미정**(06): 몇 미만이 "확인 필요"인지 값이 없음 → 구현 시 임의값 위험.

## J. 그래서 v10을 어떻게 준비하나 (우선순위 재조정)
설계 순서(4-1부터)는 **뼈대가 서 있을 때** 맞다. 지금은 밑이 없어서 순서를 바꾼다:

**0순위 (블로커):** 프로덕션 서버(onrender) 소스 확보·연결. 이거 없이는 4-1 불가 + "서버=진실" 미성립.

**1순위 (뼈대 이설, v9 안 건드리고):** expand-and-contract로
- 서버에 **contribution 테이블 신설**(클라 UUID·불변·추가형) — 기존 trips 옆에 **병행**, 백필. 파괴적 변경 금지(심사 중 v9 안전).
- 클라에 **UUID 발급 + 멱등 재전송** 추가.
- 삭제/수정을 **소프트삭제·조정기여**로 전환(하드 PUT/DELETE 단계적 폐기).

**2순위:** 4-1 매칭을 **새 기여 모델 위에서** 서버 매처로 구현(1건 자동/다건 확인/0건 inbox). 영수증 POST를 기여로 편입.

**3순위:** driver_type를 **능력 플래그 프로파일**로 승격(네이밍 private/corp 확정) → 그 위에 05 계약콜(minRole:corp) 얹기.

**병행:** 등록소 v2/근무시간/온보딩 **문서 실물 복원**(단일 출처 완성), 길드·랭킹 위치를 로드맵에 반영(방향 결정).
