## 1. 테마 = 색 (다크 기본 / 라이트 보조)
**결정:** 지금 코드에 하드코딩된 색(#0A0E1A 등)을 **토큰으로 모아** `theme` 값 하나(`dark`|`light`)로 스위치. 다크가 기본(야간운행), 라이트는 낮·실내 보조.
- **근거:** 원칙 1(값으로 흡수 — 새 테마 = 값 추가), 원칙 6(한 톤·일관성).
- **경계:** 이건 **색**이다. 배치(튜닝모드, §3)와 **다른 축.** 섞지 말 것.
- **선행작업:** 색 토큰 추출(디자인 토큰화)이 먼저. 이게 끝나야 라이트가 "값 하나"로 붙음.
- **액션:** 색 토큰화 → light 팔레트 1벌 → 설정 스위치. (v10 4-5 다듬기와 함께 or 직후)
- **검증:** 두 모드에서 모든 카드가 한 시스템으로 보이나? 야간 눈부심/주간 가독 대비 OK?

## 2. 온보딩 해상도 막힘 — **버그(우선), 아이디어 아님**
**결정:** **반응형+스크롤(본치료) + 뒤로가기→홈(안전망)** 둘 다.
- **근거:** 북극성 정면 위반("첫 3분에 막힘") + 원칙 7(막지 말고 잡기). 테스터 이탈 직결이라 **우선순위 최상.**
- **본치료:** 온보딩 고정크기 제거 → 스크롤로 감싸고 **"다음" 버튼 하단 고정**(항상 보이게). 어떤 해상도(작은폰·폴더블 접힘·큰 글꼴 접근성)든 안 막힘.
- **안전망:** 그래도 막히면 **뒤로가기로 닫고 홈 진입**(로드맵 "뒤로가기→홈"과 일치). 단 이건 보조 — 온보딩을 건너뛰는 것뿐이라 본치료가 우선.
- **버린 안:** "작게 만들기" = 임시방편(작은 화면에선 또 막힘).
- **액션:** OnboardingScreen(MainActivity)의 Dialog/Column을 스크롤+반응형으로. 하단 버튼 sticky.
- **검증:** 최소해상도 3종(예: 720p·폴더블 접힘·글꼴 최대)에서 "다음"이 항상 보이고 눌리나?

## 3. "튜닝모드" = 화면 등록소 v2 (배치 커스터마이즈)
**결정:** 루이가 이름 붙인 **"튜닝모드"의 실체 = 화면 등록소 v2** — 기사가 홈·탭의 **카드를 직접 켜고/끄고/순서 바꾸는** 것. 색(테마)과 별개 축.
- **근거:** 원칙 1(배치를 값으로 흡수), 원칙 6(카드 3규격·한 톤은 유지하고 **위치만** 바꿈 → 조잡해지지 않음).
- **경계:** 자유 색상 커스터마이즈 아님. "내 화면을 내가 튜닝"하되 **틀(규격·톤)은 시스템이 지킴.**
- **뼈대 구멍:** 화면 등록소 v2 **설계문서 실물이 정본에 없음**(진단 09-G1). "튜닝모드"라는 사용자 대면 이름이 생겼으니, **등록소 v2 문서를 복원하며 이 네이밍 반영**해야 함.
- **액션:** 등록소 v2 설계문서 복원(카드 등록소·slot·defaultVisible·minRole) + UI 이름 "튜닝모드"로.
- **검증:** 카드 배치를 바꿔도 3규격·한 톤이 유지되나? 유형(driver_type)별 minRole 카드가 자동 노출/숨김되나?

## 4. driver_type — 개인/법인 유지, 조합 "자리만" + 온보딩 신원 최소수집
**결정:**
- **유형:** 지금은 **개인 / 법인** 2종만 UI 노출. **조합(cooperative)은 값으로 자리만** 예약(문서 04 "3번째 유형은 자리만" 그대로). 가맹 등은 수요 보고.
- **코드값(권장):** 지금 서버가 이미 `personal`/`corporate`로 **실데이터를 저장 중** → 설계의 private/corp로 바꾸면 **기존 유저 데이터 마이그레이션 비용**이 생김. 그래서 **코드 현행값을 정본으로 채택**하고(=`personal`|`corporate`|(예약)`cooperative`) **설계문서 04의 표기를 코드에 맞춰 통일**하는 걸 권장. (원칙 2 단순함 · 원칙 3 살아있는 데이터 안 흔들기.)
- **온보딩 신원:** 유형은 **필수**, 이름·소속 등은 **유형에 따라 필요한 것만 + 스킵 가능**. 개인=소속 안 물음(본인 사업자), 법인=회사명·사번, 조합=조합명. → 온보딩에서 과하게 물어 이탈시키지 않음(원칙 5·북극성 "첫 3분").
- **근거:** 문서 04 그대로. 유형이 "무슨 정보를 물을지"까지 값으로 가름 → if 분기 폭발 없음.
- **코드 현실:** 서버 users에 이미 `nickname·company_name·car_number·employee_id·work_type` 존재. 유형 노출 + 조건부 필드만 얹으면 됨.
- **액션:** ① driver_type 코드값 확정(personal/corporate + cooperative 예약) ② 온보딩에 유형 선택 + 유형별 조건부 신원필드(스킵 가능) ③ 등록소 minRole을 유형에 연결(§3과 맞물림).
- **검증:** 조합 추가가 값 하나로 되나(분기 없나)? 유형별 온보딩 질문이 자동으로 갈리나? 최소 필수 + 나머지 선택인가?
