## 1. 실제 스키마 (v10이 딛는 땅)
```
trips(
  id SERIAL PK, user_id INT,
  origin, destination TEXT,
  origin_lat/lng, dest_lat/lng NUMERIC,
  platform TEXT,               -- '카카오'|'길빵/예약'|...
  fare INT NULL,               -- ★ 비어 있을 수 있음 = 4-1의 표적
  started_at, ended_at TIMESTAMP,
  is_report BOOL,              -- 전표 총매출(회사제출) 행 표시, 일부 계산서 제외
  payment_type TEXT,           -- 'cash'|'auto'|...
  source TEXT,                 -- 'manual'|'auto'|...
  editable BOOL
)
receipts(                      -- 지금은 '연료/경비 영수증' 성격 (trip_id 없음)
  user_id, type, type_name, amount,
  receipt_date, receipt_time, memo,
  liters, price_per_liter, distance, duration, raw_text
)
users( id, kakao_id, device_id, nickname, driver_type,
       company_name, car_number, employee_id, work_type, points, total_trips )
```
- 4-1의 뜻: **GPS/자동 운행 중 `fare`가 비어 있는 것**에, 늦게 들어온 **전표 금액**을 **시간·플랫폼으로 맞춰 채운다.**
- 현재 `PUT /api/trips/:id/fare`는 이미 **trip_id를 아는 상태**(접근성 감지)에서만 덮어씀 → "어느 운행인지 모르는 전표"를 붙이는 진짜 매칭은 없음.

## 2. 갈림길 (정직하게 — 헌장 "예스맨 금지")
4-1을 짓는 방법이 셋인데, 서로 상충한다. 무엇을 고르든 **하나는 골라야** 다음이 진행된다.

### 경로 A — 설계 정석 (기여/불변·추가형 전면 도입)
02·03 설계 그대로. trips를 파생으로 바꾸고 contribution 테이블로 전환.
- 👍 자가복구·투폰·오삭제복구·재연결이 **구조적으로** 풀림. 4-1이 그 위 자연스러운 한 조각.
- 👎 솔로 개발자에게 **가장 큰 공사.** 기존 stats/insights/ranking 쿼리 다수가 trips를 직접 읽어서, projection 전환 시 광범위 수정. v9 직후 리스크 큼.
- 헌장 충돌: 원칙 3(데이터 신성)엔 최상, 원칙 2·5(단순함·덜어냄)엔 과함.

### 경로 B — 실용 최소 (현 스키마에 매칭만 얹기)
trips 구조 그대로 두고, **매칭 레이어 + 미매칭 inbox**만 추가.
- 👍 가장 빠르게 v10 출시. 기존 쿼리 안 건드림.
- 👎 멱등·소프트삭제·투폰은 여전히 미해결(4-1만 됨). 덮어쓰기 방식이라 유저 정정 보호가 약함.
- 헌장 충돌: 원칙 2엔 맞고, 원칙 3(신성)엔 미흡.

### 경로 C — 중간(권장) — "싸고 값진 안전"만 먼저 + 매칭
전면 event-sourcing은 **미루되**, 데이터 신성의 **핵심 위험 2개만** 싸게 잡고 4-1을 얹는다.
1. **멱등:** trips에 `client_uuid` 추가 → 삽입을 `ON CONFLICT(client_uuid) DO NOTHING`. (재전송·투폰 중복 운행 방지. 컬럼 하나 + 클라 UUID 발급.)
2. **소프트삭제:** DELETE를 `status='deleted'`로. (오삭제 복구 = 헌장 원칙 7 "잡기". 컬럼 하나 + 쿼리 필터.)
3. **4-1 매칭 + 미매칭 inbox:** 아래 §3.
- 👍 헌장 원칙 2·3·5·7을 **동시에** 만족(과하지 않게 진짜 위험만). 전면 refactor 없이 자가복구의 80%를 값싸게.
- 👎 "운행=기여의 파생"이라는 순수 모델은 아직 아님(그건 데이터 더 쌓인 뒤 A로 승격 가능).
- **내 추천:** C. 이유 — 헌장의 "단순함이 최고 기술 + 데이터는 신성"을 **둘 다** 지키는 유일한 지점. A는 지금 과투자, B는 신성 미달.

## 3. 4-1 매칭 설계 (경로 B·C 공통, 비파괴)
### 새 테이블(추가만, 기존 불변 — v9 안전)
```sql
-- 아직 어느 운행에도 못 붙인 전표 금액 보관함 (절대 안 버림 = 데이터 신성)
CREATE TABLE IF NOT EXISTS fare_inbox (
  id SERIAL PRIMARY KEY,
  user_id INT NOT NULL,
  amount INT NOT NULL,
  platform TEXT,
  occurred_at TIMESTAMP,        -- 전표상의 거래시각(있으면)
  raw_text TEXT,
  status TEXT DEFAULT 'pending',-- 'pending'|'matched'|'confirmed'|'discarded'
  matched_trip_id INT,          -- 붙은 운행
  created_at TIMESTAMP DEFAULT NOW()
);
-- 감사 로그(되돌리기용): 어떤 fare를 어떤 근거로 채웠나 (덮어쓰기여도 흔적 남김)
CREATE TABLE IF NOT EXISTS fare_matches (
  id SERIAL PRIMARY KEY,
  trip_id INT, inbox_id INT, user_id INT,
  amount INT, method TEXT,      -- 'auto'|'user_confirm'
  created_at TIMESTAMP DEFAULT NOW()
);
```
### 매처 (전표 금액 1건 들어올 때)
```
후보 = trips WHERE user_id=? AND fare IS NULL
        AND (platform 일치 or platform NULL)
        AND started_at BETWEEN occurred_at - 15min AND occurred_at + 15min   -- 시간창
- 후보 1건  → trips.fare 설정 + fare_matches(method='auto') 기록 + inbox.status='matched'
- 후보 0건  → fare_inbox(status='pending') 보관 (버리지 않음)
- 후보 2건+ → inbox 'pending' + 후보목록 반환 → 앱이 "확인 필요"로 유저 선택(자동추측 금지)
```
- **단일 자동, 다건 확인, 0건 보관** = 설계 4-1 그대로. 같은 플랫폼 다건은 OCR 시각이 못 쪼개므로 **추측 안 함.**
- 시간창(±15분)·플랫폼 매칭은 `driver_settings` 값으로 뺄 수 있게(회사별 조정). 지금은 상수.

### 엔드포인트(신규, 기존 라우트 불변)
```
POST /api/fare-inbox            {user_id, amount, platform?, occurred_at?, raw_text?}
                                → 매처 실행, {result:'auto'|'confirm'|'stored', candidates?}
GET  /api/fare-inbox/:user_id   → status='pending' 목록(확인함 화면)
POST /api/fare-inbox/:id/assign {trip_id}  → 유저가 후보 선택 → fare 채움 + 기록
```

## 4. 클라이언트(앱) 변경 — 최소
- (경로 C) 운행 생성 시 **client_uuid 발급**(랜덤 UUID)해서 `POST /api/trips`에 포함.
- 전표 OCR 결과(금액·플랫폼·시각)를 `/api/trips/:id/fare` 덮어쓰기 대신 **`POST /api/fare-inbox`** 로 보냄 → 서버 매처가 붙임.
- "확인 필요 전표" 배지/화면(다건일 때 후보 목록에서 탭). 기록탭에 자연히 얹힘.
- **driver_type 네이밍:** 지금 앱 `personal/corporate` ↔ 설계 `private/corp`. **여기서 확정**(둘 중 하나로 통일 후 서버 `driver_type` 값 정리). 능력 플래그(hasQuota 등)는 이후 05 계약콜 붙일 때 도입.

## 5. v9를 안 건드린다는 증거 (expand-and-contract)
- 위 변경은 **전부 추가(ADD COLUMN / CREATE TABLE / 신규 라우트)** — 기존 컬럼·라우트·쿼리 **불변.**
- 그래서 심사 중 v9(=현재 배포본과 동일 계약)와 충돌 없음. v10은 **v9 통과 후 배포**, 그 전까지 서버는 추가분을 조용히 준비만.
- 배포 순서: 서버 추가분 먼저(하위호환) → 앱 v10에서 새 경로 사용.
