## 1. 운영 격리 — 이전 보고를 정정한다

**정정.** 앞서 "앱은 `Config.SERVER_URL` 전환으로 붙인다" 고 썼다. **틀렸다.**
`Config.kt` 주석이 "서버 주소 한 곳 관리" 라고 되어 있어 그걸 믿었고, 실제 요청 목적지를 세지 않았다.

전수 스캔 결과 (`_handover_20261002/measure/urls_20261005.txt`, `node _scan_urls.js`):

| | 수정 전 | 수정 후 |
|---|---|---|
| 운영 URL 하드코딩 | **27파일 34곳** | **1곳** (`Endpoint.kt:27` = `Endpoint.PROD` 자체) |
| `Config.SERVER_URL` 경유 | 9파일 | — (Config 는 Endpoint 로 넘기는 껍데기) |

즉 `Config.SERVER_URL` 만 바꿨다면 **나머지 요청은 전부 운영으로 갔다.**
`WorkAutoEndReceiver` 뿐 아니라 `TrackSync` · `BackupSync` · `SettingsSync` · `Feedback` ·
`TimingLog` · `InsightsActivity`(7곳) · `WorkSessionService`(2곳) 등이 다 그랬다.

### 바꾼 것

`app/src/main/java/com/callradar/app/Endpoint.kt` 를 **유일한 출처**로 만들었다.

- `Endpoint.PROD` 문자열은 이 파일에만 존재한다. 다른 곳의 리터럴 34개는 `Endpoint.base` 로 치환.
- **기본값은 운영이다.** 아무 설정이 없으면 운영으로 간다 — 실수로 검증 서버를 보지 않게.
- 전환은 **디버그 빌드에서만** 가능하다(`BuildConfig.DEBUG` 검사). release 는 override 를 읽지 않는다.
  스토어에 나간 앱이 검증 서버를 보는 사고를 코드로 막는다.
- 전환 키는 `callradar_prefs` 의 `server_url_override`. UI 를 만들지 않았다(오조작 방지), adb 로 넣는다.
- 값 검증: `http://` 또는 `https://` 로 시작하고 공백이 없을 때만 받는다. 아니면 운영으로 되돌린다.

### 진입점마다 init

`MainActivity` 하나만으로는 부족하다 — 아래 경로들은 MainActivity 없이 깨어난다(부팅·알람·접근성 이벤트·알림).
여기서 안 부르면 **그 경로의 요청만 조용히 운영으로 나간다.**

| 진입점 | 왜 |
|---|---|
| `MainActivity.onCreate` (동의 게이트보다 먼저) | 게이트·서비스 기동이 이미 서버를 친다 |
| `WorkAutoEndReceiver.onReceive` | 알람으로 별도 깨어남 |
| `WorkSessionService.onCreate` | 부팅·서비스 재시작 |
| `FloatingTripService.onCreate` | 플로팅 |
| `NaviIntentReceiver.onServiceConnected` | 접근성 |
| `MeterFloatingService.onCreate` / `LocationTrackingService.onCreate` | 서비스 |

### 남은 확인 (미완)

- **실제 요청 목적지 런타임 확인은 아직 안 했다.** 코드상 리터럴은 1곳이지만, 기기에서
  override 를 넣고 `logcat`/프록시로 **모든 요청이 로컬로 가는지** 세어야 확정이다.
  통합 후보 설치 때 이 확인을 넣는다.
- 외부 도메인은 그대로 둔다(카카오맵 타일, nominatim, mymemory, 공항 API 등) — 운영 DB 와 무관.

## 2. 스키마 동일성 — **보장됐다고 쓰지 않는다**

**정정.** 앞서 "스키마는 index.js 가 스스로 만든다 → 운영과 같은 모양이 보장된다" 고 썼다. **과한 표현이었다.**
기동 시 생성은 **현재 코드가 만드는 초기 스키마**다. 운영 DB 는 그와 별개로 마이그레이션 이력·수동 변경을
지나왔고, 인덱스와 제약은 특히 어긋나기 쉽다.

### 지금 확보한 것

로컬 검증 DB 지문 (`_handover_20261002/measure/schema_local.json`):

```
40 tables / 335 columns / 121 constraints / 60 indexes
server_version_num = 170006   (PostgreSQL 17.6)
```

### 운영과의 차이 — **미대조**

| 항목 | 상태 |
|---|---|
| 테이블 목록 | 미대조 |
| 컬럼 존재·타입·nullable·default | 미대조 |
| 제약(PK/UK/FK/CHECK) | 미대조 |
| 인덱스 이름·정의 | 미대조 |
| 마이그레이션 이력 | 미대조 |

**차단 사유:** 운영 DB 외부 접속 URL 이 없다. `server/.env` 의 롤은 로그인이 거부된다
(`role "callradar_db_user" is not permitted to log in`).

**대조 도구는 미리 만들어 뒀다.** URL 이 들어오면 두 명령으로 끝난다:

```
DBURL=<운영 외부 접속 URL>  node calc/test/schema_dump.js prod
                            node calc/test/schema_compare.js
```

`schema_dump.js` 는 `information_schema` / `pg_indexes` 만 읽는다(쓰기 없음, 30초 타임아웃).
비밀값은 출력하지 않는다.

### PG 버전 차이 — 기록

| | 버전 |
|---|---|
| 운영 (Render `dpg-d8l2h4ernols73c9p7o0-a`) | **PostgreSQL 18** |
| 로컬 검증 | **PostgreSQL 17.6** |

메이저 1 단계 차이다. 이 차이가 영향을 줄 수 있는 범위:
기본값 표현, `ORDER BY` 의 동률 처리, 플래너 선택(= 성능 측정 결과), 일부 함수의 기본 동작.
**따라서 로컬에서 측정한 성능 숫자를 운영 성능으로 쓰지 않는다.** 기능 동작(멱등, 제약 위반,
부분 저장) 검증에는 이 차이가 영향을 주지 않는다고 판단하되, 그 판단도 대조 후 재확인한다.
`schema_compare.js` 가 메이저 버전이 다르면 경고를 찍는다.

## 3. 통합 앱이 의존하는 서버 계약

지시 6: 서버 변경이 필요하다는 이유로 필수 기능을 후보로 바꾸지 않는다.
검증 환경에서 구현·시험을 끝내고 **운영 반영만 승인 대기**로 둔다.

### 3.1 지금 운영에 이미 있는 것 (앱이 바로 의존해도 되는 계약)

| 계약 | 운영 상태 | 비고 |
|---|---|---|
| `GET /api/trips/:user_id` 에 `toll` 포함 | **반영됨** (`6c8cc37`, Live 확인) | 구버전 앱에도 효과 |
| `POST /api/track/points` — `(user_id, ts)` 멱등 | 있음 | `ON CONFLICT DO NOTHING` |
| `POST /api/track/points` — 3000점 상한, 초과분 무시 | 있음 (결함) | 앱이 1000점 분할로 회피 |
| `GET /api/track/points/:userId?since=&until=` | 있음 | 되짚음 확인에 사용 |
| `POST /api/work-session` | 있음 | |
| `POST /api/work-session/close` | 있음 | 자동마감은 아직 호출하지 않는다 |
| `GET /api/today/:id` | 있음 | 44,700원 기준점 검증에 사용 |

### 3.2 서버 변경이 필요한 것 — 검증 환경에서 완료, 운영 반영 승인 대기

| ID | 변경 | 왜 필수인가 | 검증 상태 |
|---|---|---|---|
| S1 | `POST /api/track/points` 가 **실제 저장 수**와 **처리한 마지막 ts** 를 반환 | 지금은 `inserted` 가 '시도한 행 수' 라 ACK 로 못 쓴다. 앱이 읽기로 되짚어야만 확인된다(요청 2배) | 설계만. 구현 미착수 |
| S2 | 상한 초과를 **200 으로 숨기지 말고 206/400 으로 알림** | 조용히 버리는 것이 유실의 원인이었다 | 설계만 |
| S3 | 자동마감이 `/api/work-session/close` 를 호출 | 지금은 `work_start=0` 만 밀어 서버 `work_sessions_log` 에 세션이 안 닫힌다 | 앱·서버 양쪽 미착수 |
| S4 | 집계·캐시에 `calc_version` / `data_version` / `as_of` | 숫자가 바뀐 이유(계산 변경 vs 자료 변경)를 구분할 수 없다 | 설계만 |
| S5 | 대기시간 질의를 `observed/censored/unknown` 3분할로 | `COALESCE(wait,15)` 평균을 못 쓴다. 순수 함수(`waitstats.js`)는 3분할 입력을 받게 돼 있다 | 순수 함수 완료, SQL 미착수 |

**앱은 S1~S5 없이도 동작하게 만든다.** 그래야 운영 반영이 늦어도 통합 후보를 설치할 수 있다.
구체적으로:
- S1/S2 없이: 앱이 1000점 분할 + 읽기 되짚음으로 **확인된 범위까지만** 워터마크를 올린다(구현·검증 완료).
- S3 없이: 자동마감은 로컬 세션 로그에 남고 서버 세션은 0 으로 밀린다. **서버 `work_sessions_log` 에
  자동마감 세션이 없다는 사실을 화면이 표시**해야 한다(미착수 — E19 관측과 함께).
- S4 없이: 새 계산 결과에 `calcVersion` 을 **앱 쪽에서** 붙여 들고 다닌다(미착수).
- S5 없이: 대기 통계는 **자료 부족 표시**로 나간다. 가짜 평균을 내지 않는다.

## 4. 궤적 수정의 정확한 성격 — **배치 상한 초과 방지**

**정정.** 앞서 "부분 처리 후 ACK 를 고쳤다" 고 썼다. 과한 표현이다.
1,000점 분할은 **재현한 문제(상한 초과분 유실)를 해결**하지만 **진짜 ACK 가 아니다.**
서버는 어느 점이 저장됐는지 돌려주지 않고, `inserted` 는 `ON CONFLICT DO NOTHING` 때문에
실제 신규 저장 수와도 다르다. 점별 ACK 는 S1 — 운영 반영 승인 대기 항목이다.

앱이 할 수 있는 선까지만 했고, 그 선은 **"확인된 범위까지만 워터마크를 올린다"** 다:

| 응답 | 워터마크 |
|---|---|
| `inserted >= 보낸 수` | 덩어리 마지막 ts 까지 올린다 |
| `0 < inserted < 보낸 수` | **`inserted` 번째 점의 ts 까지만** 올리고 멈춘다 (slice 는 앞부터 자른다) |
| `inserted == 0` | 올리지 않고 멈춘다 |
| 본문을 못 읽음 | **올리지 않고 멈춘다** — 모르면 올리지 않는다 |
| 비 2xx | 올리지 않고 멈춘다 |

그리고 **읽기로 되짚는다**(`verifyWatermark`): 올린 워터마크가 서버 실제 보유분보다 앞서 있으면
**되돌린다**. 지금 가능한 유일한 진짜 확인이다.

### 검증 결과 — 지시된 5개 실패 상황 (로컬 서버 + 로컬 PG, 19건 전부 통과)

`server/calc/test/r03_ack_scenarios.js`

| 상황 | 결과 |
|---|---|
| ④ 부분 저장 (상한 초과, 4000점) | 4000점 전부 저장, 워터마크 = 마지막 점, 되짚음 통과 |
| ① 중간 배치 실패 (3번째 덩어리 네트워크 끊김) | 2000점까지만 저장, 워터마크가 그 지점에서 멈춤(건너뛰지 않음), 재실행으로 4000점 완성 |
| ② 저장 후 응답 유실 | 서버엔 1000점 들어갔지만 **앱은 워터마크를 올리지 않음**. 재실행 후 2000점, 중복 없음 |
| ③ 중복 재전송 | 워터마크를 일부러 되돌려 재전송 → 1500점 그대로, 중복 생성 0 |
| ⑤ 앱 재시작 | 덩어리마다 커밋돼 있어 1000점 지점이 남고, 재시작 후 이어받아 3500점 완성 |
| 되짚음 롤백 | 서버가 덜 가진 경우 워터마크를 되돌린다 |

**남은 한계:** 3일 창 밖 구간은 서버 미러에 공백이 남는다. 창 확대는 부하 측정 전에는 하지 않고
`track_gap_from/to/count` 로 가시화만 했다.

## 5. 자동마감 — 진행 중 콜 보호 (지시 3)

**정정.** "FloatingTripService 를 멈추지 않으니 진행 중 운행은 안전하다" 는 판단은 **불충분했다.**
코드를 따라가 보면 마감이 그대로 돌 때 이렇게 된다:

1. `work_start=0`, `work_distance_m=0`, `meter_local=false` 로 근무 상태 초기화
2. `WorkSessionService` 정지 → **진행 중 콜의 남은 거리가 아예 측정되지 않는다**
3. 그 콜이 끝나 저장되면 운행은 남지만, 방금 닫힌 세션 로그에는 `fare: 0` → **매출이 세션 밖으로 떨어진다**
4. 콜 종료 후 다음 운행이 시작되면 자동출근이 **새 세션**을 열고 또 15시간 예약이 걸린다
   → 마감이 '무한 누적 방지' 가 아니라 **'15시간짜리 구간 분할'** 로 동작한다

### 바꾼 것

**운행 중에는 마감하지 않고 미룬다.** 운행이 떠 있다는 것은 기사가 일하고 있다는 증거이고,
손님을 태운 채로 근무를 끊는 것이 더 나쁘다.

- 진행 중 판정은 **디스크 상태**로 한다 — 이 수신기는 별도 프로세스로 깨어나므로 서비스의
  메모리 변수를 볼 수 없다. `auto_trip_id > 0`(자동기록) 또는 `ride_active`(수동 플로팅).
- 30분씩, **최대 8회(4시간)** 유예. `WorkAutoEnd.scheduleAt(now + 30분)` — `workStart` 를 바꾸지
  않으므로 **'연장' 이 아니라 '유예'** 다.
- 유예 카운터는 세션에 묶인다(`autoend_defer_ws = work_start`). 다른 세션 카운터가 이월되지 않는다.
- 유예 때 기사에게 알린다 — '왜 마감이 안 됐지' 하지 않게.
- 상한 초과 시에는 마감하되 `autoend_closed_mid_trip` 을 남긴다.
- 자동출근이 마감 직후(30분 내)에 붙으면 `WorkAutoEnd.noteChainedAutoStart` 가
  `work_chain_count` / `work_chain_root` / `work_chain_last_gap_ms` 를 남긴다.
  **자동출근을 막지는 않는다** — 막으면 그 운행의 시간·거리가 아예 안 잡힌다.
  대신 집계가 '실제로는 한 번 출근' 임을 알 수 있고, 관측(R15)이 반복을 찾아낼 수 있다.

### 아직 검증 못 한 것

- 유예·사슬 동작의 **실기기 확인**. 15시간 경과가 필요해 `work_start` 를 과거로 조작한 모의
  시험이 필요하다(실제 자료를 건드리지 않는 테스트 계정에서).
- 진행 중 콜의 매출 귀속을 **세션에 되돌려 넣는 것**은 아직 안 했다. 현재는 '세션 밖 운행' 으로
  표시될 뿐이다(순수 함수 `worktime.js` 의 `tripOutsideWorkMs` 가 그것을 드러낸다).
  세션 로그의 `fare: 0` 도 그대로다 — R06 계약 확정 대기.
