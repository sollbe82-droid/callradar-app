# 콜레이더 — 멀티소스 기록 뼈대 설계
*작성 2026-07-21 · 4대 확장 뼈대 ② "기록/데이터 = 멀티소스" · v10 최우선(4-1 전표금액 매칭)의 기반*

> 설계헌장 통과: 최적안 + 반박/대안 + 뼈대 연결 + 검증 체크리스트.
> 핵심 통찰: **멀티소스 기록과 데이터 자가복구는 같은 등뼈다.** 둘 다 "덮어쓰지 말고 불변·추가형 기여로 쌓고, 보이는 운행은 파생."

---

## 1. 최적안 — 운행은 '저장'이 아니라 '기여들의 합(projection)'
**한 운행(Trip)을 하나의 레코드로 덮어쓰지 않는다.** 각 입력방식이 **기여(Contribution)** 를 하나씩 얹고, 화면에 보이는 운행은 그 기여들을 합친 **파생값**이다.

- GPS = 출발지/도착지·시간 기여
- 전표 = 금액·플랫폼 기여
- 현금 = 현금 수령액 기여 ("숨은 현금 잡기")
- 수동 = 유저가 직접 고친 값 기여 (**항상 최고 우선**)
- (나중) 스샷·미터기 BLE·AI = 기여 하나씩 추가

→ **새 입력방식 = 소스 하나 추가.** 병합 엔진과 운행 UI는 안 바뀐다. (본체 불변 · 한 줄 추가)

---

## 2. 데이터 모델
```js
// 보이는 운행 = 파생(projection). 저장이 아니라 계산됨.
Trip = {
  id,
  derived: {                    // contributions에서 계산
    startDong, endDong, startTime, endTime, path,
    platform, fare, cash, tip, ...
    _provenance: { fare:'meter', startDong:'gps', cash:'cash', ... } // 각 필드 출처
  }
}

// 기여 = 불변·추가형 (자가복구 저널과 동일 원칙)
Contribution = {
  id,                 // 클라이언트 생성 UUID → 멱등(재전송해도 중복 안 됨)
  tripId,             // 어느 운행에. 아직 못 붙였으면 null → 미매칭함(inbox)
  source,             // 'gps'|'meter'|'cash'|'manual'|'screenshot'|'ble'|'ai'
  fields,             // 이 소스가 기여하는 값: { fare:42000, platform:'kakao' }
  time,               // { at } 또는 { range:[start,end] } — 매칭용
  confidence,         // 0.0~1.0 (OCR/추론 신뢰도)
  status,             // 'active'|'superseded'|'rejected' (되돌리기용, 덮어쓰기 아님)
  createdAt, deviceId,
}
```

## 3. 소스 등록소 (새 입력방식 = 한 줄)
```js
export const SOURCES = {
  gps:    { contributes:['startDong','endDong','startTime','endTime','path'],
            precedence:{ location:100, time:100 }, matcher:null /* 운행 자체를 생성 */ },
  meter:  { contributes:['fare','platform','count'],
            precedence:{ fare:90 }, matcher:'byTimeAndPlatform', confidence:'ocr' },
  cash:   { contributes:['cash','tip'], precedence:{ cash:100, tip:100 },
            matcher:'currentOrManual' },
  manual: { contributes:['*'], precedence:{ '*':999 } },   // 유저 정정이 항상 최고
  screenshot:{ contributes:['fare','platform'], precedence:{ fare:80 },
            matcher:'byCompletionMoment' },               // v10+ 별도심사(⑥)
  ble:    { /* 나중: 미터기 승객상태 */ },
  ai:     { /* 나중: 스샷 만능입력 */ },
}
```

## 4. 병합 규칙 — 결정론적·재계산 가능
```js
function projectTrip(tripId) {
  const cs = contributions(tripId).filter(c => c.status === 'active')
  const derived = {}, provenance = {}
  for (const field of ALL_FIELDS) {
    const winner = cs.filter(c => field in c.fields)
                     .sort(byPrecedence(field))[0]        // 유저정정 > 권위소스 > 추론
    if (winner) { derived[field] = winner.fields[field]; provenance[field] = winner.source }
  }
  return { derived, provenance }
}
```
- **대원칙:** 자동 소스는 **유저의 수동 정정을 절대 못 덮는다**(precedence 999). 자가복구 헌장과 일치.
- 파생은 순수함수 → 기여를 더하거나 다시 연결하면 자동 재계산. **손상 시 재계산 = 자가치유.**
- 성능: 파생값을 캐시(materialize)해 두고 기여 변경 시에만 재계산.

## 5. 매칭 엔진 = v10 최우선(4-1) 그 자체
전표는 운행보다 늦게 들어온다(사진을 나중에 찍음). 늦게 온 **전표 기여를 올바른 GPS 운행에 연결**하는 게 4-1.
```
새 meter 기여 도착 →
  후보 = 운행들 중 (플랫폼 일치) & (시간대 겹침) & (금액 아직 비어 있음)
  · 후보 1건  → 자동 연결 → 금액 자동 채움 ✅
  · 후보 0건  → 미매칭함(inbox)에 보관 (절대 안 버림)
  · 후보 2건+ → "확인 필요"로 유저에게 후보 제시 (자동 추측 금지)
```
- **단일 건만 자동**, 같은 플랫폼 다건은 OCR이 거래시간을 못 쪼개므로 **추측하지 않고 확인 요청.** (실수 잡기)
- 미매칭 전표는 버리지 않고 inbox에 남아 나중에 수동/AI로 연결. (데이터는 신성)
- 나중 AI = 다건일 때 "이 금액은 이 운행 같아요" **제안만**(승인은 유저).

## 6. 반박 / 대안 (내가 내 안을 먼저 깐다)
- **"기여 모델은 무겁지 않나?"** — 맞다, 단순 레코드보다 간접적이다. 그런데 이건 **동시에 자가복구 저널**이고(한 구조로 두 문제 해결), 4-1의 늦은-연결·재연결·투폰 병합을 **안전하게** 만드는 유일하게 깔끔한 길이다. 그래서 채택하되 **범위를 축소:** 운행·수입(금융)만 기여 모델, 사소한 설정은 평범한 값.
- **"그냥 운행을 수정하고 변경로그만 남기면?"** — 그러면 늦게 온 전표를 어느 운행에 넣을지, 투폰 충돌을 어떻게 합칠지가 다시 지옥이 된다. 기여+파생이 그걸 구조적으로 없앤다(병합=합집합).
- **단순함 지키기:** 소스는 처음엔 gps·meter·cash·manual 4개만. screenshot/ble/ai는 자리만(등록소 한 줄). 80%를 지루하게 튼튼히.

---

## 7. 뼈대 연결
- **자가복구:** 기여 = 불변·추가형 금융 저널. Trip은 파생이라 손상 시 재계산으로 회복. **두 설계가 같은 등뼈.**
- **화면 등록소 v2:** 운행·수입 카드가 projection을 읽어 표시. 각 값에 출처 배지(provenance) 가능.
- **법인/개인 축(driver_type):** 소스 구성·precedence를 driver_settings 값으로 흡수(회사마다 다르게).
- **정체성:** 현금 소스가 자연스레 공존 → "숨은 현금 잡기"가 구조로 실현.

---

## 8. 구현 순서 (v10 최우선부터)
1. **기여 저장(불변·추가형) + Trip projection(파생)** — 기존 운행을 이 모델로 이관, 동작 증명.
2. **SOURCES 등록소 + 병합 우선순위**(유저 정정 최고).
3. **meter 매처**(단일 자동연결 / 다건·미매칭은 확인함) = **4-1 완성.**
4. **cash·manual 소스.** 이후 screenshot/ble/ai = 등록소 한 줄씩.

## 9. 검증 체크리스트
- [ ] 새 입력방식 추가가 `SOURCES` 한 줄 + producer만으로 되나(병합·UI 무수정)?
- [ ] 자동 소스가 유저 수동 정정을 절대 못 덮나?
- [ ] 전표 다건·모호 매칭에서 자동 추측 안 하고 "확인 필요"로 빠지나?
- [ ] 미매칭 전표가 버려지지 않고 inbox에 남나?
- [ ] Trip이 기여들에서 재계산되어 손상 시 자가치유되나?
- [ ] 같은 UUID 기여 재전송이 중복 운행/금액을 안 만드나(멱등)?
- [ ] 각 필드의 출처(provenance)가 표시되나?
- [ ] 투폰 두 기기 기여가 합집합으로 병합되어 충돌·유실이 없나?
