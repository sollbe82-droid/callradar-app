### R03 — 궤적 동기화 (부분 ACK·페이지 전송·오프라인 원본 보존)

> **정정 (2026-10-05 15:20).** 앞선 판정 "궤적은 로컬 전용·서버 업로드 없음"은 **틀렸다.** 근거로 삼은 것은
> `LocalTrackDatabase.kt:12` 의 주석 한 줄이었고, 실제 전송 코드를 찾지 않았다. `TrackSync.kt` 에
> 업로드·복원이 다 있고 `MainActivity`·`HomeScreen`·`TrackActivity` 가 호출한다. 주석을 코드로
> 검증하지 않은 분류 오류다. 아래는 코드와 서버 핸들러를 직접 읽고 다시 쓴 것이다.

- **상태: 구현(동작 중) / 확정 결함 3건 — 그 중 1건 이번 빌드에서 수정**
- 확정 현황:
  - `TrackSync.uploadRecent()` → `POST /api/track/points`, 8초 다운샘플, 좌표 소수 5자리, 워터마크 `track_upload_ts`
  - `TrackSync.fetchRange()` → `GET /api/track/points/:userId?since=&until=` (로컬에 없을 때 복원)
  - 서버 `index.js:5813` 는 `ON CONFLICT (user_id, ts) DO NOTHING` 으로 멱등. 보관 31일. 좌표는 키가 설정돼 있으면 `lat_e/lng_e` 암호문 칸에 저장(`locEnc`).
- **확정 결함 ① 부분 처리 후 ACK — 자료가 영구 유실된다. (이번 빌드에서 수정)**
  - 서버 `index.js:5818` 이 `pts.slice(0, 3000)` 으로 **초과분을 조용히 버리고 200 을 준다.**
  - 앱은 2xx 만 보고 `track_upload_ts` 를 **배치 전체의 마지막 ts** 로 올렸다.
  - 3일 창 × 8초 다운샘플 = 최대 약 **32,400점**. 3000점만 저장되고 워터마크가 32,400점 뒤로 가므로 **남은 약 29,400점은 다시 올라가지 않는다.** 서버 미러에 영구 공백.
  - 서버의 `inserted: vals.length` 도 `DO NOTHING` 때문에 '시도한 행 수'이고 실제 저장 수가 아니다 → **ACK 로 신뢰할 수 없다.**
  - 수정: 1000점 단위로 끊어 보내고, **덩어리가 2xx 로 끝날 때 그 덩어리의 마지막 ts 까지만** 워터마크를 올린다. 실패하면 그 자리에서 멈추고 다음 실행이 재개한다. `track_upload_fail_at` / `track_upload_fail_code` 기록. **서버 변경 없이 성립** — 배포 금지 상태에서도 유효하다.
- **확정 결함 ② 페이지 전송 없음** — 고치기 전에는 최대 약 1.4MB JSON 단일 POST. 0.1 CPU DB 에 한 번에 32,400행 INSERT. ①의 수정으로 함께 해소(1000점 ≈ 45KB).
- **확정 결함 ③ 창 밖 구간은 서버 미러에 영구 공백** — `since = max(last, now−3일)`. 3일 넘게 업로드가 안 되면(장기 오프라인·기기 꺼짐) 그 구간은 건너뛰고 워터마크는 전진한다. **로컬 원본은 남으므로 자료가 사라지는 건 아니다.** 창을 넓히는 것은 부하 측정 전에는 하지 않고, 대신 `track_gap_from/to/count` 로 **공백을 가시화**하도록만 바꿨다. 창 확대 여부는 R14 측정 후 결정.
- 미측정: 실제 전송 성공률, 서버 `track_points` 테이블 크기·증가량, 복원 경로(기기변경)의 실동작, 암호화 키 회전 시 못 푸는 점의 비율
- 남은 작업: 서버가 **실제 저장 수를 돌려주게** 하는 것(진짜 ACK). 이건 서버 변경이므로 별도 승인. 그 전까지는 앱의 덩어리 경계가 ACK 대용이다.
- 의존성: §7 보유기간 정책, R13(권한), R14(비용)

### R08 — 유사 과거 상황 (조건부 대기 분포·방향·표본·최신성·후퇴)

- **상태: 설계**
- 확정(결함): 대기시간 통계가 `COALESCE(wait,15)` + `LEAST(…,90)` 로 **결측을 15분으로 채우고 90분에서 자른다.** 이 상태의 평균을 "기대 대기시간"으로 쓸 수 없다.
- 요구 반영: `observed / censored / unknown` 을 **각각 세고** `observation_rate` / `censoring_rate` / `unknown_rate` 를 분리한다. `censored_rate = 1 − 관측률` 은 unknown 을 섞으므로 쓰지 않는다.
- 요구 반영: 관측 완료 사례만의 평균은 **조건부 통계**로 명시한다. "편향 없는 기대 대기시간"으로 표시 금지.
- 남은 작업: 세 비율 분리 집계 → 표본 수·지역/시간 범위·최신성 표시 → 자료 부족 시 후퇴 규칙
- 의존성: R06, R12

### 2.5 남은 작업 / 이번 빌드에서 한 것

**이번 후보 빌드에 포함 (지시 1)**
- 결함 1 수정 — `FloatingTripService.ensureWorkSessionActive()` 에 자동마감 예약 추가.
  - **OFF 존중**: `work_max_hours_set` 이 true 이거나 값이 0 이 아니면 건드리지 않는다. 미설정일 때만 15 기본값. `WorkAutoEnd.schedule(…, 0)` 은 내부에서 `cancel` 로 빠지므로 15시간을 강제하지 않는다.
  - **연장 방지 검증(코드로 확정)**: `WorkAutoEnd.schedule` 의 발화시각은 `triggerAt = workStart + maxHours*3600_000` 이다. '지금'이 들어가지 않는다. 따라서 ① 운행이 여러 번 시작돼도 ② 일시정지→재개가 반복돼도 ③ 같은 호출이 중복돼도 마감 시각은 **밀리지 않는다**. 전달하는 값도 `pushWs`(기존 세션이면 기존 `work_start`, 새로 출근했으면 그 시각)이고 `now` 를 넣지 않는다. 재부팅으로 알람이 날아간 세션은 같은 식으로 **원래 시각에** 되살아난다.
  - **WorkResume 는 schedule 을 부르지 않는다** — 재개가 workStart 를 바꾸지 않으므로 기존 알람이 그대로 유효하다. 이것이 "재개가 마감 시각을 연장하지 않는다" 의 근거다.
  - **진행 중 운행·미전송 보호(코드로 확정)**: `WorkAutoEndReceiver` 는 `work_*` prefs 와 `WorkSessionService` 만 건드린다. `FloatingTripService`(진행 중 운행을 들고 있는 쪽)를 멈추지 않고, `trips`·로컬 미전송 큐를 건드리지 않는다. `last_work_start` / `last_work_paused_total` / `last_work_end` 이어가기 스냅샷도 남는다. 조기·스테일 발화는 `now - workStart < threshold - 60초` 일 때 **재예약 후 종료**로 방어돼 있다(연장이 아니라 원래 시각으로 재예약).
  - **남은 품질 문제(미수정, R06 대기)**: 자동마감이 세션 로그에 `fare: 0`, `perHour: 0` 을 쓴다. "기록 없음"과 "실제 0원"을 구분하지 못하는 바로 그 사례다. 계약 확정 전에는 손대지 않는다.
  - **남은 문제(미수정, 서버 변경 필요)**: 자동마감은 `/api/work-session` 에 `work_start=0` 을 밀 뿐 `/api/work-session/close` 를 부르지 않는다 → 서버 `work_sessions_log` 에 세션이 안 닫힌다. 서버 배포 금지 상태이므로 열린 건으로 기록.

## 3. 금액 대조: 39,900 vs 44,700 (§11.1)

**오류로 단정하지 않았다. 구성 항목으로 분해한 결과는 다음과 같다.**

`GET /api/trips/1` (운영, 읽기 전용) 에서 영업일 2026-10-05 (KST) 에 해당하는 운행 5건:

| trip id | 시각 (KST) | 플랫폼 | fare | tip | promo | toll | 결제 | 좌표 |
|---|---|---|---|---|---|---|---|---|
| 37369 | 10-05 07:09 | 길빵/예약 | 4,800 | 0 | 0 | 0 | card | **0,0** |
| 37325 | 10-05 07:15 | 카카오T | 4,800 | 0 | 0 | 0 | auto | 있음 |
| 37326 | 10-05 07:24 | 카카오T | 4,800 | 0 | 0 | 0 | auto | 있음 |
| 37329 | 10-05 07:32 | 카카오T | 12,000 | 0 | 0 | 0 | auto | 있음 |
| 37336 | 10-05 08:03 | 카카오T | 18,300 | 0 | 0 | 0 | auto | 있음 |
| **합계** | | | **44,700** | **0** | **0** | **0** | | |

- `GET /api/today/1` → `{"tripCount":5,"todayFare":44700,"todayTip":0,…}` — **운행 원본 합계와 정확히 일치. 확정.**
- **차액 4,800원 = trip 37369 한 건과 정확히 같다** (44,700 − 39,900 = 4,800). 확정.
- **추정**(미검증): 37369 는 `started_at` 이 07:09 로 **소급 입력**된 수동 기록(길빵/예약, `promo_type="프로모션"`, 좌표 0,0)이다. 세션 2082 가 마감된 시점에는 이 건이 아직 없어서 `fare_total` 이 39,900 이었고, 이후 입력되어 현재 44,700 이 되었다 — 라는 설명이 차액과 정확히 맞는다. 다만 `created_at` 을 확인해야 확정된다. `/api/trips` 는 `created_at` 을 반환하지 않으므로 **DB 조회가 필요하고, 외부 DB 접속 URL 이 없어 수행하지 못했다.**
- **별도 미해결(확정된 불일치):** 세션 2082 의 `gross_min`/`net_min` = 251 분인데, 제가 기록해 둔 세션 구간은 10:46→11:07 (21분)이다. `per_hour` 9,504 × 4.19h ≈ 39,900 이므로 **251분 쪽이 `per_hour` 와 정합**하고, 제가 적어둔 시각 쪽이 틀렸을 가능성이 크다. 이것도 DB 재조회로만 확정된다.
- **따라서 둘 중 어느 숫자도 "오류"로 판정하지 않는다.** 앱/API 일치는 확인됐지만 그것만으로 실제 금액의 정확성이 입증되지 않는다는 점도 그대로 유지한다.

**데이터 품질 항목(새로 발견, 확정):** 37369 는 `promo_type="프로모션"` 인데 `promo=0` 이다. 프로모션 금액이 0 인 프로모션 건이다. R06 의 "팁은 별도 표시해도 총수입에서 누락하지 않는다" 와 같은 성격의 문제 — 유형은 있고 금액은 없는 상태를 어떻게 다룰지 계약에 넣어야 한다.
