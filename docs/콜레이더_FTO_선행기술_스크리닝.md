## 발명 A — 무입력(접근성) 기반 복수 택시앱 데이터 자동수집·정규화

- **선행기술**: 접근성 API로 화면 UI를 읽어 기록/추출하는 일반 기술은 이미 존재(미국특허·학술 다수). 즉 "접근성으로 화면 데이터를 읽는다"는 넓은 개념은 **공지기술**.
- **FTO 위험: 중간** — 넓은 청구항(접근성 데이터 캡처 일반)은 남의 권리와 겹칠 수 있음.
- **우리 차별점(=특허성 확보 지점)**: "**복수 이종 택시 호출·내비 앱**의 서로 다른 화면을 **표준 포맷으로 정규화·합산**" + "Knox/FLAG_SECURE 차단 상황 대응". → 청구항을 **택시 다중플랫폼 정규화**로 좁히면 신규성 있고 침해 회피 가능.
- **조치**: 청구항을 좁게(택시·정규화·합산 한정). "접근성 캡처 일반" 독립항은 피함.

## 발명 B — 다수 기사 비식별 제보 기반 지역·시간대 수요예측 + 수락률 지표

- **선행기술**: 라이드헤일링 수요예측은 **학술·공개 자료가 매우 많음**(LSTM 등). Uber/Lyft/Didi는 **자사 디스패치 데이터** 기반 예측·서지 특허 보유.
- **FTO 위험: 중간(방법 특정 시 낮음)** — 공개 학술이 많아 남이 "넓게" 막기 어렵지만, 우리도 넓게는 못 냄.
- **우리 차별점**: 플랫폼 내부 데이터가 아니라 "**비가맹 포함 다수 기사의 비식별 제보**" + "**호출 수신 대비 수락률**로 수급불균형 산출" — 플랫폼 사업자 특허와 데이터 출처가 다름.
- **조치**: "크라우드소싱 제보 + 수락률" 조합을 구체 청구항으로. 순수 예측 알고리즘 자체보다 **데이터 수집·검증 파이프라인**에 무게.

## 발명 C — 서버에서 파싱규칙 내려받아 이종 앱 화면 무중단 학습·개선

- **선행기술**: 원격 설정/룰 다운로드(remote config)는 일반적. 단 "**화면 파싱규칙을 서버에서 갱신해 앱 UI 변경에 무중단 대응**"의 특정 결합은 흔치 않음.
- **FTO 위험: 낮음.** **특허성: 있음(방법 특정 시).**
- **조치**: "이종 앱 UI 변화 → 서버 규칙 갱신 → 재배포 없이 파싱 유지"의 절차를 청구항화.

## 발명 D — 디지털 명함 + vCard QR 반강제 연락처 저장(단골 확보)

- **선행기술**: vCard·QR 명함 자체는 공지. 그러나 "**택시 기사–승객 단골화**를 위한 저장 유도 + 앱 연계"라는 **용도·결합**은 신선.
- **FTO 위험: 낮음.** **특허성: 조건부 있음** — 단순 QR 명함은 진보성 약함 → **자동 재호출/단골 매칭·안전문구·앱연동** 등 부가 구성과 결합해야 권리성↑.
- **조치**: 명함 단독이 아니라 "명함→연락처저장→재호출/단골 파이프라인" 결합으로 출원.

## 발명 E — 이벤트(야구·콘서트·크루즈) 기반 택시 수요예측 피드

- **선행기술**: 이벤트 기반 수요예측 개념은 존재(교통/상권). 
- **FTO 위험: 낮음.** **특허성: 약함(단독)** — B(크라우드소싱)와 **결합**할 때 의미.
- **조치**: 독립 출원보다 B의 종속항/실시예로 편입.

- **가장 안전하고 새로운 것: C(서버 규칙 다운로드), D(명함 단골화 결합).** 본출원/추가출원 우선.
- **가장 조심할 것: A·B의 "넓은" 청구항** — 남의 권리와 겹칠 수 있으니 **좁고 구체적인 방법**으로.
- 공통 원칙: **넓은 독립항 욕심내지 말고, 우리만의 구체 구성(택시·정규화·크라우드검증)으로 좁히면** 침해도 피하고 등록 확률도 올라감.
